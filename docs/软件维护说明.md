## 从源码运行

- 系统：Windows 10 / 11（64 位）。Python 用 3.14（`requirements.txt` 开头写明了锁定时的版本和环境）。
- 在项目根目录建虚拟环境并装依赖：

  ```powershell
  py -3.14 -m venv .venv
  .venv\Scripts\python -m pip install --no-deps -r requirements.txt
  ```

  `requirements.txt` 是完整的锁定清单（含间接依赖），装时加 `--no-deps`：pip 只装这里列出的版本，不再自己解析依赖。文件开头的注释说明了为什么（原版 `rapidocr` 的元数据要求带图形界面的 opencv-python，本项目只用 opencv-python-headless，两者共用同一个 `cv2` 目录、不能同时装）。装好后 `pip check` 会提示「rapidocr 需要 opencv-python」，属预期，可以忽略。开发者机器上如果装过 opencv-python，按文件开头的命令换成 headless 版。
- 打包另需 `requirements-build.txt`（Nuitka 和 ziglang，见「打包发行版」）。
- 启动开发版：在项目根目录运行 `.venv\Scripts\python -m advisor.ui`。报错直接打在这个命令行窗口里；启动失败时另弹消息框，错误也写进项目根目录的 `.tmp\overlay_err.txt`（见 `advisor/errors.py`）。不想留命令行窗口时改用 `.venv\Scripts\pythonw -W ignore -m advisor.ui`，这时报错只看那个文件。启动和启动失败的检查在 `advisor/ui/startup.py`，入口是 `advisor/ui/__init__.py` 的 `run()`。开发版全部展开时标题栏写「拾星助手 开发版」，发行的版本写「拾星助手」，免得和同版本号的发行版混淆。
- 命令行推荐（调试、对照用）：`.venv\Scripts\python -m advisor --hero 凛 --star 1 --round 4 --offer 标靶 标记喷罐 鹰眼瞄具`。另有 `--owned`、`--map`、`--source`、`--tier`、`--difficulty normal`（普通难度）或 `--difficulty nightmare`（噩梦及以上）、`--progress-cap`、`--progress`、`--left-rarity`、`--tasks-done`、`--rerolls`（或 `--rerolls-used`；两个都不给时按一次都没用过推算，同悬浮窗读不出刷新次数时，不按多出来的刷新算）、`--teammates 凛 邦妮:电脑`、`--mutators`、`--json` 等，完整列表见 `advisor/cli.py`。筹码名和资料库对不上时按最像的筹码计算，并在错误输出里提示一句。
- 文字识别用随仓库的 `rapidocr_lite/`（精简版，见「目录结构」）：开发时它从装好的原版 `rapidocr` 包里找模型，发行的版本里模型放在 `app\models`（打包时拷进去）。
- 测试和基准用环境变量 `ACC_TODAY`（合法的 `YYYY-MM-DD`）钉死「今天」，不设时用系统日期。
- 文件位置一律通过 `advisor/paths.py` 取得（`app_dir`、`data_dir`、`assets_dir`、`download_dir`、`fonts_dir`、`state_path`、`schemes_path`、`logs_dir`、`reports_dir`、`temp_dir` 等），开发目录和发行的版本用同一套代码。运行中生成的东西（设置、筹码方案、下载的识别图片、推荐日志、诊断包、临时文件）在开发版里放在项目根目录（识别图片在 `assets/` 下），发行的版本里放在程序目录；其中设置和筹码方案优先放个人目录 `%APPDATA%\AstralChipCompass`，下载的识别图片、两份下载记录和手动指定角色时存的立绘模板优先放个人目录 `%LOCALAPPDATA%\AstralChipCompass\assets`（所有版本共用一份，换新版本只下新出的和改过的），写不进时退回程序目录，见 `advisor/paths.py`。随发行版带的星数横条模板和皮肤缩略图照旧在程序目录的 `assets` 下（`assets_dir`）；读写下载的识别图片一律用 `download_dir`，不要用 `assets_dir`。

## 目录结构

```text
拾星助手/
├─ README.md              首页（只做导航、声明和最短的介绍）
├─ CONTRIBUTING.md        参与改动须知
├─ AGENTS.md              给 AI 编程工具的入口
├─ .github/ISSUE_TEMPLATE/  反馈问题的两份表单：问题反馈、游戏更新了
├─ LICENSE  LICENSES/  THIRD_PARTY_NOTICES.md   许可证和第三方声明
├─ requirements.txt  requirements-build.txt     运行依赖、打包依赖
├─ advisor/               程序本体：识别、记账、推荐、悬浮窗
├─ rapidocr_lite/         精简的文字识别库（随程序发布）
├─ data/                  游戏数据和推荐规则（游戏更新时改的就是这里）
├─ mechanics/             游戏机制说明（讲机制，数值在 data/）
├─ review/                推荐规则的审查清单（生成，不手改）
├─ tools/                 检查、生成、下载、打包脚本和开发工具
├─ tests/                 单元测试（详见 docs/测试指南.md）
├─ docs/                  说明和文档
├─ fonts/  assets/        皮肤用的字体；随仓库附带的图片（其余识别图片第一次运行时下载）
└─ packaging/             打包入口和启动程序
```

下面逐项说明每个文件夹、每个代码文件放什么。`advisor/` 下按子文件夹列到每个 `.py`；`tests/` 只说测试放在这里，各测试文件见 [测试指南.md](测试指南.md)；`data/` 下每个文件的字段见「数据结构」；`mechanics/`、`review/`、`docs/` 见各自的文件夹一行。

| 路径 | 内容 |
|---|---|
| `advisor/__init__.py`、`__main__.py` | 包的对外接口（`Advice`、`State`、`advise`、`load_db` 等）和命令行入口（`python -m advisor`） |
| `advisor/engine/`、`advisor/pool.py` | 打分、前瞻、刷新、剩余三选一次数推算、筹码池和概率；按筹码方案排先后（位次、同一档按档位前瞻排、收入降档、会少拿必选和推荐的往后排、刷新按档位的比较、选择后无法获得的提醒和附注）。引擎是一个包，对外的名字都从 `advisor.engine` 导入：`scorer.py`（`Scorer` 和 `advise`）、`context.py`（一次推荐的上下文，和一帧几次推荐共用的筹码池、分布缓存）、`parts.py`（打分各分项）、`chances.py`（之后选到某筹码的概率）、`lookahead.py`（前瞻，和按方案档位算的档位前瞻）、`reroll.py`（刷新的估值）、`advice.py`（推荐的组织）、`scheme_rank.py`（按筹码方案排先后）、`advice_text.py`（界面、命令行、诊断包共用的写法） |
| `advisor/data.py` | 读 `data/` 下的数据和推荐规则，名称模糊匹配（`DB.match_chip`）；资料对不上时降级运行、不拒绝启动，问题记进 `DB.warnings`（适配表整份读不出记进 `DB.problems`） |
| `advisor/session/` | 一局的状态记账：新的一局（可撤销）、星数、星币数、难度、地图、队友、畸变组件、补录、不支持的情况；切换筹码方案后按当前画面重算。记账是一个包，对外的名字都从 `advisor.session` 导入：`core.py`（读数的入口和编排）、`game_state.py`（这一局的状态，撤销就是换回旧对象）、`selection.py`（三选一界面的状态机）、`newgame.py`（新一局的判定）、`offgame.py`（对局外画面的规则表、对局结束）、`panel.py`（「查看筹码」面板核对）、`difficulty.py`（难度合并）、`events.py`（事件、事件的序号和记录） |
| `advisor/prefs.py` | 设置的读写（state.json）：`Settings`（跨对局的设置）、读时逐项核对类型（某一项不对只这一项按默认）、写盘（经 `advisor/fileio.py`；当场只试一次、不等，被占用时交给后台写的线程 `SettingsWriter`）。记账和悬浮窗共用，对局状态不存盘 |
| `advisor/schemes.py` | 筹码方案：档位和顺位、适用地图、目标流派的推导、复制默认推荐、方案文件的读写（备份、读坏时另存、来自更新版本时只读）、分享格式（可读文字、短字符串） |
| `advisor/hub.py` | 作业站的几个固定地址（首页、某个角色的方案列表）、接口地址、地图短名和拼地址的函数，以及入口的总开关 `ENABLED`；只用标准库、不导入 Qt，界面各处都从这里取地址 |
| `advisor/hub_api.py` | 作业站的接口：按编号取一套方案（`parse_ref` 认编号和方案网址，`fetch_scheme` 只发编号、网址里的随机码和程序版本）；电视式短码登录（`request_device_code` 要短码，`poll_device_token` 等用户在网页上授权、换回令牌，`store_login` 存进凭据管理器）、本机有没有登录（`login_nickname`，只读凭据管理器、不联网）、查登录的账号（`me`）、退出（`logout`，网站上作废，本机的令牌不管网站回什么都删掉）；发方案、改方案（`publish_scheme`、`update_scheme`，只发分享码、名称、短说明、程序版本、资料日期）。网站回的内容不可信：只认约定的 JSON、正文最多 64 KiB、不跟重定向，要用户打开的网址必须是作业站的 https 地址；出错一律抛 `HubError`，带种类（`KINDS`）给界面分提示，异常里没有令牌和回话内容；401 时删掉本机的令牌。只用标准库、不导入 Qt，界面在后台线程里调用 |
| `advisor/wincred.py` | 作业站登录令牌在 Windows 凭据管理器里的存取：普通凭据，只存在这台电脑、这个 Windows 账号下；令牌按 UTF-8 存成字节，超过系统上限拒存；登录时记下的昵称存在用户名一栏，能单独读（`load_user`，界面显示「已登录」用）；存、取、删、查都不抛异常，失败只把错误码写进错误记录，不写令牌；不是 Windows 时一律当作没有 |
| `advisor/paths.py` | 文件位置：程序目录（发行的版本里是 `app` 子文件夹）和界面上的写法、个人目录（`%APPDATA%` 下的设置和筹码方案，`%LOCALAPPDATA%` 下的下载的识别图片）、个人目录写不进时的退回；用户会发给作者的文字（诊断包、错误记录、另存的崩溃记录）里用户目录、账户名换成占位（`scrub_paths`） |
| `advisor/fileio.py` | 统一的写盘：整份写入（先写临时文件、刷盘、再替换，可留 `.bak`）、读坏时另存为 `.broken-时间` 并改读备份、追加日志、诊断包这类先写进 `.partial` 文件夹再改名；`wait=False` 时被占用不等、报 `Busy` |
| `advisor/errors.py` | 错误记录（程序目录 `.tmp` 里的 overlay_err.txt）：用户目录、账户名写进去之前换成占位；一律追加；几个线程同时写时加锁；同一个错只整条记一次，之后每分钟一行「又出现 N 次」；超过约 1 MB 时旧的另存 |
| `advisor/win32.py` | 截屏、找窗口、热键、窗口层次共用的 Win32 函数声明（`ctypes` 的 `WinDLL`、参数和返回值类型、常量）；不导入 Qt |
| `advisor/sysinfo.py` | 本进程和这台电脑的运行状况：向 Windows 声明本进程要高性能；读回省电设置和优先级；读处理器、内存、电源、显示器（宽高、缩放、刷新率）、显卡，写进诊断包 |
| `advisor/perfstats.py` | 识别各步耗时和处理器占用的统计（每帧识别、文字识别、各项读数、算推荐、界面线程定时器晚到多少、进程和整机占用），写进识别记录和诊断包；另有 `usage_snapshot`/`usage_percent` 给 `advisor/usage.py` 用 |
| `advisor/usage.py` | 本进程处理器占用的采样：运行中每分钟一条（另存进程序目录的 `logs\usage.jsonl`，重启以后还在，只留最近 12 小时；每条带当时的电源状况），导出诊断时写成诊断包里的 `usage.jsonl`，并现量各线程的占用和调用栈（写进诊断包 state.json 的 usage_probe）；不导入 Qt |
| `advisor/unlock.py` | 设置文件里 `aux` 一项的存取（加密、带校验、只认这台电脑）和转账的拆账 |
| `advisor/clock.py` | 统一的时钟（测试和基准用 `ACC_TODAY` 钉死「今天」） |
| `advisor/cli.py` | 命令行推荐的参数解析和输出 |
| `advisor/assets.py` | 第一次运行时按 `data/assets_manifest.json` 下载识别图片：整个下载每秒最多开始 5 个请求、同时 6 条连接（请求的疏密只由每秒的上限管，连接多是为了在图床回话慢的时候别的连接照样在下），向接口要地址时 50 张一批、隔 2 秒；被站点防护拦下（HTTP 567、拿到拦截页面、连着被限流等）时整体停下，冷却到点再以较慢的速度接着下，冷却记录是运行时写在识别图片文件夹里的 download-cooldown.json（规矩见模块说明）。清单里带 `crop` 的角色照下载 BWIKI 上的卡面原画，核过校验值以后按裁法裁出角色照（裁图在 `advisor/vision/cardcrop.py`，由 `advisor/ui/services.py` 接上，第一次要裁图时才导入），卡面不落盘；齐不齐按识别图片文件夹里 manifest-local.json 记的「按哪张卡面、哪份裁法裁的」判断，对不上的重下卡面再裁。个别图片一直下不了（一轮失败的总张数不超过 20 张，`FAILED_MANY`，不分哪一类：写不进、wiki 上已删除的也算进去）时，其中网络出错等这一张自己的问题的失败日期记进 manifest-local.json，当天启动不再自动下载、隔天再试（点「重试」时先去掉这几张的记号、马上下：这一下正好被站点防护拦下时冷却到点接着下，又下不了的重新记）；失败超过 20 张（像断网、磁盘满了）、这一轮被拦下或取消了、下载线程建不了下载会话（读不了系统的证书、代理设置不对等，原因以 `NO_SESSION` 开头）时不记。悬浮窗那一侧（`advisor/ui/overlay_parts/background.py`）要下的不超过 100 张（`DOWNLOAD_PAUSE_OVER`）时下载期间识别照常，多的才暂停；给了 `stats` 时填这一轮的总用时、张数、有没有被拦或提前停下、连接数和最慢的 5 张（见 `download` 的说明），悬浮窗下完记进识别记录（`download_stats`） |
| `advisor/winhttp.py` | 下载识别图片、检查和下载更新用的 HTTPS/HTTP 客户端：`ctypes` 调用系统自带的 `winhttp.dll`，复用连接、跟随重定向（不跟 https→http），cookie 不收不带；代理照 `urllib.request.getproxies()` 的口径；`Session.stream` 边收边交给调用方（检查更新、下载新版本用，不把整个回话读进内存；按字节段取时另能在读正文之前核对回话头、限定最多收多少）；`Session.post` 发对局报告（任何状态码交回、不跟重定向，回话正文最多读 64 KiB 用来看错误原因）；`Session.send` 同 `post`，方法任选、另交回话头（作业站的接口用）。用它替代标准库的 `ssl`、`http.client`，发行的版本不必再带 OpenSSL |
| `advisor/update.py`、`update_files.py`、`update_apply.py`、`update_log.py` | 软件内更新（见「软件内更新」）：查有没有新版本、下载、解压备好（`update.py`）；按文件只下变了的部分（`update_files.py`：文件清单的生成和核对、从发行包里按字节段只取变了的文件拼出新版本，本身不联网）；换版本程序和新旧版本之间的几个调用（`update_apply.py`：只用标准库和 advisor 最底层的几个模块，不导入界面库、识别库）；查更新、下载、换版本共用的记录和上限（`update_log.py`） |

## 发生什么变更改哪里

数据源是 `data/` 下的 JSON 和 TOML，游戏更新以后直接改这些文件，再跑 `tools/check_data.py` 检查。`mechanics/` 里的机制文档只讲游戏机制，改数据时照它核对，但数值和效果原文以 `data/` 为准。`data/` 下的 JSON 有统一的排法，手改后排乱了运行 `python tools/check_data.py --format` 重排（见「数据结构」）。下面一条变更一份清单，每条写清改哪个文件的哪一部分、改完跑什么。

### 游戏改了一张筹码的效果

1. 改 `data/chips.json` 里那张筹码的 `effect`（效果原文，只用于显示，分数不从它算）。
2. 强弱跟着变时改同一张筹码的 `base`（基础分，是另一列手填值，不是从效果算的）。
3. 改 `data/meta.json` 的 `data_date`（资料同步日期）为当天。
4. 改 `data/synergy.toml` 里那张筹码规则的 `reason`（推荐卡片上显示的理由，要跟新效果一致）；`score` 看强弱调，依据是攻略和实际打法（规则上面常有注释写明为什么这么给分）。
5. 跑 `tools/check_data.py`；改了适配表就重新生成 `review/` 两份清单（见「推荐规则与审查」）；跑 `test_data`、`test_data_robust`、`test_engine`。

### 出了新筹码

1. `data/chips.json` 加一条（字段见「数据结构」；基础分、成长轮次、标签、流派、职业分值、适配角色照 BWIKI「筹码」页的推荐分表填）；要出现在升星/筹码商店的最左格，就加进 `pools`。`hant` 要填游戏繁体中文界面里的名字，照游戏原文抄，不自己转换。
2. `data/chip_codes.json` 补分享用的编号：`tools/check_data.py --add-codes`（只追加、不改已有的编号）。
3. 图标：`tools/fetch_chip_icons.py` 下载到 `assets/chips/`，再跑 `tools/make_assets_manifest.py` 更新 `data/assets_manifest.json`。
4. 打分：`data/synergy.toml` 里按特性或角色补规则；数值参数进 `data/rules.toml`。
5. 同系列（同一个 `icon`）：`data/series.toml` 里每两张都写一对 `[[pair]]`、每一对都写 `reason`，否则 `tools/check_data.py` 报错。
6. 地图专属筹码：`chips.json` 里写 `maps`（地图直接发全员的写 `granted` 为真）。
7. 跑 `tools/check_data.py`，跑 `test_data`、`test_series`、`test_assets_manifest`、`test_chip_panel`。

### 筹码改名或移除

1. 改 `data/chips.json` 里的 `name` 或删掉那一条。
2. `data/chip_codes.json` 里对应的那一条编号保留、不再使用：改名时把旧名写进 `old_names`，移除时标 `removed`（编号只增不改，已经分享出去的筹码方案靠它解码）。
3. 跟着改引用旧名的地方：`data/synergy.toml`、`data/series.toml`、`data/rules.toml` 里的筹码名；图标和 `data/assets_manifest.json` 里对应那张。
4. 跑 `tools/check_data.py`、`test_data`、`test_check_data`。

### 出了新角色

1. `data/heroes.json` 加一条（字段见「数据结构」）；`hant`、`hant_title`、`hant_full_name` 填游戏繁体中文界面里的名字、称号、全名，照游戏原文抄，不自己转换。
2. `data/synergy.toml` 补一段 `[[hero]]`（特性、推荐流派、依据），照现有的一段写。
3. 游戏内置推荐把新角色列为哪些筹码的适配 / 普通适配角色：照 BWIKI「筹码」页的推荐分表，补进 `data/chips.json` 里那几张筹码的 `fit`、`fit_minor`。

### 出了新皮肤、WIKI 上没有角色照

认角色比对的是角色照（`UT_Hero_RolePhoto_*`）。BWIKI 上只有整张卡面原画（`UT_Hero_Card_*`）、没有角色照的皮肤，或者 BWIKI 上那张角色照和游戏里的不一样（裁的位置、画面不同，对局里认不出），按一份「裁法」从卡面现裁：游戏里的角色照就是从卡面裁下来、摆正、缩到 240×340 的。首次运行时下载卡面原图、在用户电脑上裁出角色照，卡面用完就删。不用游戏文件：

### 界面文字与繁体界面

界面文字（`advisor/ui/` 下各模块的文字常量）一律只写简体。界面是繁体时（`advisor/ui/lang.py` 的 `CURRENT` 为 `zh-Hant`），各界面文字模块在末尾调 `lang.localize(globals())`，把名字全是大写字母、数字、下划线的常量统一转成繁体（繁体用词和字形）；别的模块导入这些常量时拿到的就是转好的。`localize` 要放在所有文字常量定义完以后、别的模块来导入它们以前：例如设置窗口的 `dialog.py` 放在导入 `layouts`、`widgets`、`palette` 之前，这三块从 `dialog.py` 取文字常量。个别常量不能转时写进模块的 `HANT_KEEP`：两项语言名各用自己的字写、打开「关于」窗口用的节名要和 `version.about_sections` 对上、只写进错误记录的标题（各窗口出错时的 `*_LOG`、`ERROR_TITLE` 这类），以及从 `advisor.ui` 以外的模块导进来、值有汉字的大写常量（拿来比对、当键、写进文件的，例如引擎给的首推名）。日志、诊断包、对局记录、方案、分享码照旧写简体。

函数里现拼的文字、引擎和会话交来的显示文字不在模块常量里，在交给控件显示的那一处包一层 `lang.t(文字)`：界面是繁体时转、简体时原样，转换出错也原样返回。写进文件的（推荐日志、识别记录、诊断包、方案、分享码）、拿来比对、当键、正则、识别词表的一律不包。

繁体界面有一个总开关：`advisor/ui/lang.py` 的 `HANT_ENABLED`（发行版里为 `True`）。为 `False` 时界面一律简体：启动时不读设置文件里的「界面语言」，也不看 Windows 的显示语言；设置窗口不显示「界面语言」一项（`settings/dialog.py` 的 `shown_items`），底栏「设置」按钮的悬停说明不写它（`SETTINGS_TIP`，打开时用 `SETTINGS_TIP_HANT`）；认出繁体游戏时不问要不要换（下面那一行提示）；没选过的「界面语言」也不替用户填，留到打开以后再按 Windows 的显示语言定。设置文件里已经存着的值照原样留着；对照表、繁体字体照旧随发行版带着。改这个开关时，使用说明「界面导览」的设置窗口图注和「设置」一节里的「界面语言」跟着加上或去掉，设置窗口的截图重画（`tools/make_manual_images.py --only settings`）；测试按这个开关核对这几处。下面讲「界面语言」一项和认出繁体游戏那一行的两段，都是开关打开时的样子。

转换照 OpenCC 1.4.2 的 s2twp：先按词组表、单字表简转繁，再换繁体用词，最后换繁体字形。第一步先把资料库里的繁体名和人补的词组（含它们的最终写法自身）从左到右最长匹配、互不重叠地锁住，锁住的那几段不再经过后面的繁体用词和字形；剩下的空隙再按 OpenCC 的词组、单字转。这样已经转好的文字再转一遍（模块重新导出、显示处再包一层 `t()`）结果不变。对照表 `data/zh_hant.json` 是生成的，不要手改，收的是 5 份词典的全部条目（显示处现转的文字什么词都可能有）；人补的词组在 `data/zh_hant_extra.toml`。一个简体字有几种写法都对、取哪个都行的 27 个常用字，默认写法写在 `tools/hant_table.py` 的 `CHAR_DEFAULTS` 里，改了这一项也要重新生成表。资料库里的名字（`chips.json` 等的 `hant`）或 `CHAR_DEFAULTS` 改了以后，在项目根目录运行：

```powershell
.venv\Scripts\python -m tools.hant_table build
```

生成工具读 `.tmp\opencc-ver.1.4.2\` 里的 5 个词典：从 OpenCC 的 GitHub 仓库（<https://github.com/BYVoid/OpenCC>）标签 `ver.1.4.2` 下放词典的文件夹取 `STPhrases.txt`、`STCharacters.txt`、`TWPhrases.txt`、`TWVariantsPhrases.txt`、`TWVariants.txt`，原样放进这个文件夹（`.tmp` 不进版本库）。表里的 `digest` 只按资料库里的名字算，测试会核对它：名字改了却没重新生成时会报出来；改界面文字、改版本号都不用重做表。

一个简体字对应几个繁体字、词组表又没盖住、也不在 `CHAR_DEFAULTS` 里时，测试会拦下，列出模块、文字、第几个字和几个候选。照繁体的写法在 `data/zh_hant_extra.toml` 补一条 `"简体词" = "繁体词"`（写最终写法，不再经过繁体用词和字形），不用重新生成表。资料库里的繁体名和这里补的词组都是最终写法。补了词组、改了界面文字以后，转出来的繁体可能多出繁体字体子集里没有的字：跑 `test_skin_classic`、`test_skin_carbon`，缺字时照「打包发行版」的「字体子集」重做繁体的两个子集。

设置窗口选「界面语言」时交给悬浮窗的 `set_ui_lang`：存进设置文件，和当前相同时不重写；同时识别时第二张转给第一张，第一张改完抄给第二张（界面偏好两张共用一份）。〔现在重开〕交给 `restart_app`：`relaunch.start` 起得来就照托盘「退出」收尾，起不来时不退出，记一条识别记录，在悬浮窗上提示一次「没能重新打开拾星助手。请从托盘菜单选「退出」，再重新打开。」。诊断包的「悬浮窗状态」另记这次启动用的界面语言 `ui_lang`（设置文件里存的那一项另有）。

三选一完整识别连着两次读到繁体标题（`ChipSelect.hant`，只重查绿框、快速盯绿框的沿用读数不算）时，`Session.hant_game` 在这次运行里一直为真。界面是简体（`lang.is_hant()` 为假）、设置里没选繁體（选了等重开的不再提示）、这条提示也没关过时，悬浮窗在标题栏下方排一行（「免费软件」声明前面，全局提示，只有第一张显示；对局进行中先不显示，中途退出一局的见「中途退出一局」那一条）：文字和两个按钮在显示时才用 `lang.to_hant` 转成繁体（简体界面平时不读对照表）；〔換〕交给 `Overlay.switch_to_hant`（存成繁體、`restart_app` 重新打开），〔不換〕把 `UiSettings.hant_notice_closed` 记进设置文件，以后不再问；两个按钮一样宽。「说明」卡片的四个按钮在繁体界面下按钮文字和悬停说明里的节名也转成繁体，点了照旧传简体的节名。

```powershell
.venv\Scripts\python -m tools.hant_table show --all
```

`--module` 给 `.py` 文件路径或模块名都行。`--all` 看繁体界面可能显示的全部文字：调了 `localize` 的模块的常量、界面文字模块里写的全部字符串、`advisor/` 下 `lang.t()` 里写死的文字，加上 `advisor/ui` 以外、在显示处 `lang.t()` 的常量（`tools/hant_table.py` 的 `SHOWN_CONSTANTS`，现在是 `advisor/vision/capture.py` 里找不到游戏窗口的几句和平台名；一字多繁的测试也查这几条）；繁体字体子集照同一个范围收字。不给参数时只看调了 `localize` 的模块。`advisor/ui` 以外的模块新写了要显示在界面上的常量时，在显示处包 `lang.t()`，并把它记进 `SHOWN_CONSTANTS`。

### 作业站的入口

作业站是玩家分享拾星助手筹码方案的网站。「筹码方案」卡片的「作业站」按钮、导入/导出窗口的「去作业站找方案」和托盘菜单的「打开作业站」只用系统默认的浏览器打开它的固定页面，网址里不带方案内容；导入/导出窗口的「按编号导入」和「发到作业站」由程序自己连作业站（`advisor/hub_api.py`），登录信息存在 Windows 凭据管理器里（`advisor/wincred.py`，凭据名是 `hub.CRED_TARGET`）。这些入口由 `advisor/hub.py` 的 `ENABLED` 管：现在为 `False`，「筹码方案」卡片的「作业站」按钮，导入/导出窗口的「按编号导入」那一行（编号输入框和按钮）、「发到作业站」、「已登录作业站」那一行和其中的「退出作业站」、「去作业站找方案」，托盘菜单的「打开作业站」都不显示，程序也不连作业站；诊断包 `version.txt` 里「作业站登录：有／没有」那一行也只在开关打开时写，入口关着时不写，也不查凭据管理器（`advisor/diagnostics.py`）。藏着的部件照样放在原来的布局里，只是不显示：看不见的部件不占位、前后不加间距，卡片上另外两个按钮按它们两个取一样的宽度。设成 `True` 时这些入口照常显示。改这个开关时，使用说明里作业站的图注和段落（悬浮窗总览、「筹码方案」卡片、导入/导出窗口、托盘菜单的图注，「导入和导出的规则」里作业站的几条，「隐私」「声明」里联网的第四项）、「关于」窗口的隐私说明和免责声明（`advisor/version.py`）、`THIRD_PARTY_NOTICES.md` 的免责声明跟着加上或去掉，四张截图重画（`tools/make_manual_images.py --only overview,scheme-card,scheme-share,tray`）；导入/导出窗口在各套外观里打开时的大小（皮肤的 `SHARE.SIZE`）写的是入口关着时的大小，打开入口时改成 `tests/test_scheme_share.py` 的 `HUB_OPEN_SIZES` 记的大小（高度连作业站那几行算在内）；测试按开关关着的样子核对这几处。下面的表和几段讲的是入口打开时的样子。入口：

网站直接读拾星助手的分享格式（`advisor/schemes.py`）、筹码编号表（`data/chip_codes.json`）和 `data/` 里的资料。所以改了分享格式、筹码编号表或 `data/` 里的资料时，要让网站那边同步。分享格式以后要升级时：老版本读到新格式只会报「来自更新版本的拾星助手，当前版本无法导入」，不会读错；用老版本的人可以在软件里更新上来，所以新格式可以在新版本里直接写，用不到新内容的方案照写旧格式，老版本照样能导入。第 3 版就是这样，1.1.0 起直接写。换短字符串开头的字母时，老版本认不出新开头，连「来自更新版本」都不报（识别不到这一套），所以用不到新内容的方案照写老版本认得的开头。

分享格式第 3 版（可读文字「筹码方案 v3」、短字符串「ACC3-」）带方案标的适用地图：可读文字在档位后面、说明前面加「地图：龙宫游乐园、魔法学院」，短字符串在档位段后面接地图段（最大的地图编号 6 位，再从编号 1 到最大编号每张一位）。导出（复制到剪贴板）时标了地图的方案写第 3 版、没标的照写第 2 版，导入认第 2、3 版。开关是 `advisor/schemes.py` 的 `WRITE_MAPS`（开着）；关掉时导出一律写第 2 版，导出窗口在预览框下面提示分享出去的内容不带适用地图。「发到作业站」不看开关：标了地图的方案按第 3 版发上去（`hub_api.publish_scheme`、`update_scheme` 调 `to_short(..., maps=True)`），作业站认第 3 版。对局报告里的方案照写第 2 版（`maps=False`）。1.1.0 以前的版本导入不了第 3 版：可读文字报来自更新版本，短字符串的「ACC」开头它不认、识别不到。

短字符串的开头：第 3 版写「ACC」（拾星助手英文名 Astral Chip Compass 的缩写），第 2 版照写「CA」，让只认「CA」的 1.1.0 以前的版本也能导入没标地图的方案（`SHORT_TEXT`、`SHORT_TEXT_MAPS`）。导入时两种开头哪个版本都认，不分大小写、全角半角；开头不算进校验，同一串编码写成「CA3-」「ACC3-」解出来一样，网站早先给出的「CA3-」照样能导入。以后第 2 版也改写「ACC」时只改 `SHORT_TEXT`：导入和 `advisor/game_report.py` 从短字符串里取分享码的 `_SCHEME_CODE` 都已经认两种开头；收对局报告的服务器、分享方案的网站也要认得「ACC2-」。

复刻的改版改了分享格式、或者不想打开这个网站时，改 `advisor/hub.py` 的地址，或去掉这几个入口（`advisor/ui/overlay_parts/layout.py` 的「作业站」按钮、`advisor/ui/scheme_share.py` 的「发到作业站」「去作业站找方案」「按编号导入」和「已登录作业站」那一行、`advisor/ui/overlay_parts/follow.py` 的托盘菜单项，以及接在 `Overlay.open_hub` 上的接线）。

## 数据结构

`data/` 下每个文件讲清字段。改数据前先看这一节；下面提到的校验都由 `tools/check_data.py` 和 `advisor/data.py` 载入时的核对执行。

`data/` 下的 JSON 按统一的排法写：短的列表、字典写在一行（例如 `"tags": ["攻击"]`、`"class_points": {"攻击": 15}`；折成一行后连缩进和键名不超过 100 个字符的算短，一个汉字算一个字符，行末的逗号不算），长文字一个值一行，缩进 1 格。手改时排乱了、缩进不一致时，运行 `python tools/check_data.py --format` 按这个排法重写（内容不变，换行符照原文件：`data/` 下是 CRLF）；不带参数检查时排法不对会提示这一句。同一个表里写了不止一次的键（例如复制一张地图忘了改名）也会报出来，删好以前 `--format` 不重排这个文件：程序只认最后一个，照它重排会把前面那一份悄悄删掉。

### `data/chips.json`

一个对象，`chips` 数组，每条是一张筹码：

- `name`：筹码名。识别靠「名称 + 图标 + 稀有度」匹配（`advisor/vision/chip_select.py`、`chip_panel.py`）。
- `en`：英文名。
- `hant`：游戏繁体中文界面里的名字，照游戏原文抄，不自己转换；认筹码时和 `name`、`aliases` 一样认，程序内部和分享码仍用 `name`。没写时照常载入、只认简体的写法，`tools/check_data.py` 会报出来。
- `rarity`：稀有度，只能是 `蓝`、`紫`、`金`。
- `icon`：图标 ID，同系列不同档次共用一个（对应 `assets/chips/` 下以图标 ID 命名的图片，如 UT_Relic_50010.png）。
- `group`：分组（`通用`、某个流派，或地图专属分组）。
- `school`：流派（`星光`、`治愈`、`标记`、`充能`）；`group` 是流派时写这个流派，否则写 `null`。
- `maps`：地图专属筹码所属的地图（属于多张地图时都写上）；不是地图专属的写空数组。
- `granted`：为真表示这张筹码由地图开局直接发给全员。
- `effect`：效果原文，只用于显示；分数不从它算（打分只读下面的结构化字段）。
- `base`：基础分，手填的，不是从效果算出来的。
- `growth_round`：成长轮次（效果里写「成长≤N」的那种），没有写 `null`。
- `tags`：标签（`攻击`、`卡牌`、`辅助`、`生存`、`通用`），游戏内置推荐的标签分按它给。
- `pools`：最左格的职业筹码池（升星和筹码商店第一次刷出三选一时，最左格从这个池出）。
- `class_points`：职业分值（加进职业权重，用于判断角色属于哪个职业、以及最左格出哪个池）。
- `fit`、`fit_minor`：游戏内置推荐把这张筹码列为该角色的适配 / 普通适配筹码，写角色名。照游戏自带的推荐数据填（BWIKI「筹码」页的推荐分表，「适配角色」「普通适配角色」两列）：游戏不按角色特性自动列入，例如有的物理输出角色不在拳击手套-高级的适配名单里；游戏更新、出了新角色时对照这张表改。`tools/check_data.py` 只核对写的是 `heroes.json` 里的角色名，不核对名单齐不齐。

谁读它：`advisor/data.py` 载入成 `Chip`；推荐用 `tags`、`school`、`base`、`growth_round`、`class_points`、`fit`；识别用名称、`icon`、`rarity` 核对。手改注意：稀有度只能写那三个值；地图专属的 `maps` 里的地图要在 `maps.json` 里有；`tags`、`class_points` 改动会影响推荐分。

### `data/heroes.json`

一个数组，每条是一个角色：

- `id`：角色编号（皮肤文件名里用）。
- `name`、`en`、`full_name`、`title`：名称；界面上按 `title`/`full_name` 拼成「称号 · 角色名」。
- `hant`、`hant_title`、`hant_full_name`：游戏繁体中文界面里的名字、称号、全名，照游戏原文抄，不自己转换；`full_name` 和 `name` 相同的角色不写 `hant_full_name`。认角色时和上面的名称一样认，程序内部和分享码仍用简体名。没写时照常载入、只认简体的写法，`tools/check_data.py` 会报出来。
- `aliases`：识别匹配用的别名（要含 `name`、`full_name`、`title`、`en`）。
- `weights`：四个职业的权重。
- `group`：六类之一（`物理主C`、`法术C`、`辅C`、`钱辅`、`奶辅`、`功能辅`），分类和名单以 [`mechanics/characters.md`](../mechanics/characters.md) 第三章为准，两边要一致。它决定悬浮窗、编辑方案、导入/导出三处角色下拉框的先后和审查清单的分节（六类按这个顺序排，同一类里按这份文件里的前后），不参与推荐打分；`tools/check_data.py` 会核对它取的是不是六类之一。
- `atk`、`def`、`hp`：面板数值。
- `potential`：是否有潜能。

技能、潜能、等级奖励的说明文字不在这里，写在机制文档 `mechanics/characters.md` 里（程序不读，只给人看）。

谁读它：`advisor/data.py` 载入成 `Hero`；选角界面识别（`advisor/vision/hero.py`）按名称和别名匹配。

### `data/maps.json`

一个对象，键是地图名，每项：

- `file`：对应的机制文档名（在 `mechanics/maps/` 下），程序不读它，只作对照；`tools/check_data.py` 会核对这个文件存在，文件里「任务」表列出的任务名和这张地图的 `tasks` 一致。
- `tasks`：任务栏上的任务文字，照游戏原文抄。认地图靠它，推算剩余三选一次数也按它（`advisor/vision/hud.py`）。
- `hant`：游戏繁体中文界面里的地图名，照游戏原文抄，不自己转换；认地图时和简体的键一样认。
- `hant_tasks`：游戏任务栏上的繁体任务文字，和 `tasks` 一一对应、顺序相同，照游戏原文抄；拼不出来的那一条写 `null`。载入时按位置和 `tasks` 配对：第 i 条繁体就是第 i 条简体任务的另一种写法，认地图时任务栏上读到哪一种写法都算对上这一条任务，对上几条、读到几成都按任务算（繁体任务栏读全时和简体读全时得分相同）；写 `null` 的那一条只认简体的写法。`hant`、`hant_tasks` 没写时照常载入、只认简体的写法，`tools/check_data.py` 会报出来。
- `chip_tasks`：一局里奖励筹码的任务有几个（普通到疯狂相同；只在极限出现的任务不算）；有几条路线时取平均。
- `task_levels`：各难度一局的筹码任务等级，推荐用它估计之后任务三选一的稀有度（`MapInfo.task_level_shares`）。一张表，键是难度名（`普通`、`困难`、`噩梦`、`疯狂`、`极限`，没有资料的难度不写）：值是一条路线的等级列表（这条路线上每个奖励筹码三选一的任务写一个等级，1～3 级；不奖励筹码的任务不写，不必和 `tasks` 的先后对应），有几条路线时写列表的列表（推荐时各条线平均）。写了这个难度就用它；没读到难度名、只知道是噩梦及以上时用噩梦那一列；完全不知道难度、或这个难度没写时用困难那一列；整张图没写时照旧按当前星数。每条路线的等级个数要和 `chip_tasks`（极限对 `extreme.chip_tasks`）对得上，`tools/check_data.py` 会核对。
- `progress_cap`：最高难度的进度上限。
- `progress_caps`：各难度（`普通`、`困难`、`噩梦`、`疯狂`）的进度上限，没有资料的难度写 `null`。
- `extreme`：只有开放极限难度的地图写，`{"progress_cap": 极限的进度上限, "chip_tasks": 极限一局的筹码任务数}`（照游戏内核对；两项都可以不写）。推荐只在本局是极限时用它：画面上读到极限，或者进度条红叉的格数只和极限的进度上限对得上、按进度上限推算成极限（和疯狂相同时分不出，要画面上读到）；其余难度、不知道难度时照旧用上面几项。
- `limited`、`ended`、`until`：是不是限时地图、是否已结束、开放到哪天（不是限时地图时 `until` 写 `null`）。

谁读它：`advisor/data.py` 的 `map_info`、`map_tasks`、`map_task_keys`；识别认地图、界面胶囊、对局记录都走这里。手改注意：`tasks` 要照游戏原文写，地图名是键、别处引用它；`progress_caps` 和 `progress_cap` 要对得上。

### `data/mutators.json`

一个对象，键是畸变组件名，每项：

- `en`：英文名。
- `hant`：游戏繁体中文界面里的组件名，照游戏原文抄，不自己转换；没写时照常载入，`tools/check_data.py` 会报出来。
- `effect`：效果原文。
- `scope`：适用地图（通用写 `通用`）。
- `limit`：适用难度（例如 `噩梦及以上`），没有写空串。
- `hint`：选筹码提示，显示在推荐附注里。

谁读它：`advisor/data.py`；`advisor/engine` 的推荐附注（「畸变组件「X」：……（仅提示，未计入推荐度）」）。

### `data/meta.json`

只写 `data_date`（资料同步日期）。「关于」窗口显示的就是它；`tests/test_project_consistency.py` 会核对它和 `advisor/version.py` 的记录一致。

### `data/chip_codes.json`

分享筹码方案的短字符串用的编号表：`note`（说明）+ `chips` 数组，每项 `code`（编号）、`name`、`en`，改名时另写 `old_names`（改名前的名字），已移除的写 `removed`。编号只增不改：已经分享出去的方案靠它解码，改编号会读不出来。新筹码用 `tools/check_data.py --add-codes` 追加编号。现役筹码那一行的 `en` 要和 `chips.json` 里的一致（`tools/check_data.py` 会核对；已移除的筹码不核对）。

### `data/rules.toml`

数值参数，改完直接生效、不用重跑脚本：稀有度概率表（`[rarity]`，普通和困难及以上两张）、刷新次数和代价（`[reroll]`）、筹码池（`[pool]`）、游戏内置推荐公式（`[official]`，`scale` 现在为 0，只用来判断游戏的推荐角标）、前瞻和各次数的权重（`[lookahead]`）、刷新代价（`[reroll_cost]`）、默认推荐四档的分值（`[synergy]`）、我的方案的分值（`[scheme]`）、生存类筹码的加分（`[survival]`）、极限难度的加分（`[extreme]`）、推算难度时不采用进度上限的地图（`[difficulty] cap_untrusted`）、美工刀与治愈来源的预判（`[heal_knife]`）、充能、标记、星光三个流派的开套预判（`[school_build]`）、体系来源（`[sources]`：哪些筹码、哪些角色算某一种体系的来源，适配表规则的 `needs_source`、`without_source` 引用这里的名字）、推荐线、推荐度换算和同系列比较（`[advice]`、`[softmax]`）、收入折算（`[income]`）、循环往复（`[endless_cycle]`）、识别节奏和悬浮窗默认值（`[watch]`）、地图识别（`[map_detect]`）。每个参数旁写有取值依据。谁读它：`advisor/data.py` 载入时核对引用和取值范围，`advisor/engine`、`advisor/session`、`advisor/vision` 读具体参数。

### `data/synergy.toml`

适配表，三块内容：`[[trait]]` 特性规则、`[[hero]]` 角色自动层、`[[player]]` 默认推荐的档位，另有 `[[combo]]` 组合规则、`[[teammates]]` 队友调分、`[[need]]` 队友刚需。写法见「推荐规则与审查」，文件各节开头也写有说明。

### `data/series.toml`

同系列筹码（同一个 `icon`）的上位替代和对比要点：每条 `[[pair]]` 有 `low`、`high`、`strict`（是否严格上位替代）、`reason`（算或不算的理由，只给维护者看）、`low_gain`、`high_gain`（两张各多什么）、`tip`（悬停说明的效果对照）；另有 `[[starlight_use]]`（效果对照里「星光层数另有用处」按当前角色和已有筹码写的内容）。谁读它：`advisor/data.py`、`advisor/engine`。判断规矩和构建检查见「游戏改了一张筹码的效果」和 `tools/check_data.py`。

### `data/assets_manifest.json`

发行的版本第一次运行时要从吉星派对 WIKI 下载的识别图片清单：`version`、`generated`、`source`、`api`、`counts`、`download_bytes`、`items`（每项 `dir`、`file`、`title`、`url`、`size`、`sha1`，从卡面原画现裁的角色照另带 `crop`（裁法的 6 个数，照抄 `card_crops.json`；这一项的 `title`、`url`、`size`、`sha1` 是卡面的），随发行版附带的标 `bundled`）。下载代码另认清单项的 `api`（图片在另一个 wiki 上时指向那里的接口），现在的清单里没有这样的项。识别用不到的不列：编号不是 `heroes.json` 里的角色的 Q 版头像（识别找头像和生成清单都按 `advisor/vision/stars.py` 的 `profile_photo_hero` 认编号）、`sfw_skip.json` 里列的健全版。由 `tools/make_assets_manifest.py` 生成，不手改；它向 wiki 的接口要地址和校验值，被站点防护拦下、被限流时退出码 2，不写清单。

### `data/card_crops.json`

从卡面原画现裁角色照的裁法：`note`（说明）+ `crops`（角色照的文件名 → `{"card": 卡面的文件名, "affine": [6 个数]}`）。`card` 是 BWIKI 上同一编号、同一皮肤的卡面原画（`UT_Hero_RolePhoto_113_04.png` 对 `UT_Hero_Card_113_04.png`）。`affine` 是 2×3 仿射矩阵，按行写 6 个数（保留 6 位小数），作用在卡面的归一化坐标 (x/宽, y/高, 1) 上，得到角色照（240×340）的像素坐标；用 `cv2.warpAffine` 时第一列除以卡面的宽、第二列除以卡面的高（`advisor/vision/cardcrop.py` 的 `pixel_matrix`）。按比例写，BWIKI 以后换了卡面的尺寸也能用。裁的时候先按透明度把颜色乘进去（透明处是黑的，同 wiki 上的角色照），再按矩阵取样。裁法照游戏内核对，新皮肤的用 `tools/derive_card_crop.py` 推算。程序运行时不读这个文件（生成清单时裁法已照抄进 `assets_manifest.json`），不随发行版。`tools/check_data.py` 核对：写法、角色照和卡面是同一编号同一皮肤、裁法合理（不翻转、不拉斜、卡面的宽高缩放在合理的范围、角色照的中心落在卡面里）、转了角度的在 `photo_tilt.json` 里有差不过 1° 的一项、清单里有对应的项（卡面、裁法都一样；`sfw_skip.json` 里列的健全版不进清单，裁法照留）。

### `data/sfw_skip.json`

首次运行不下载的健全版角色照：`note`（说明）+ `photos`（角色照的文件名 → `[本人的分数, 别的角色的分数]`）。只用普通版的角色照也认得出的健全版列在这里：两个分数是 `tools/check_sfw_cover.py` 照认角色的比对方法算的（脸部区域在 0.4、0.6 两种缩放下和全部普通版比，取低的那个；本人的普通版里最像的一张、别的角色里最像的一张，保留三位小数），本人不低于 0.93、别的角色不高于 0.83 才列进来。`tools/make_assets_manifest.py` 生成清单时跳过这里列的；不在这里的健全版照常下载。由 `tools/check_sfw_cover.py --write` 写，不手改。程序运行时不读这个文件，不随发行版；已经下过这些健全版的电脑上，文件留着照常用来建模板。`tools/check_data.py` 核对：写法、只有健全版、对得上已知的角色照（从卡面现裁的在 `card_crops.json` 里，其余的开发目录 `assets/heroes` 里有、或者同一套的普通版是已知的角色照：开发目录里的图片是第一次运行时照清单下的话，名单里的健全版本来就没下）、清单里没有名单里的。

### `data/photo_tilt.json`

对局左下角斜着摆的角色照：`note`（说明）+ `photos`（角色照的文件名 → 角度）。个别皮肤在对局里显示的是斜着摆的整张原画，wiki 的角色照却是摆正的，直接比认不出；认角色时（`advisor/vision/hero.py`）先把表里的角色照绕脸部区域（`HERO_FACE`）的中心转这么多度、再取脸部比对。角度的约定同 OpenCV 的 `getRotationMatrix2D`：单位是度，正数为逆时针，-45～45 之间；照游戏内核对。没列出的角色照照原样比对，用户手动指定角色时存的模板也不转（存的就是对局里的样子）。文件名要是 `assets_manifest.json` 里 `dir` 为 `heroes` 的一项（或 `sfw_skip.json` 里列的健全版：已经下过的照常转过来建模板），`tools/check_data.py` 会核对文件名和角度。

## 推荐规则与审查

推荐规则都在 `data/` 下，可以直接手改，改完直接生效。

- `data/synergy.toml`：特性规则（`[[trait]]`）；角色自动层（`[[hero]]`，每个角色有哪些特性、推荐流派、只属于该角色的规则；`keep_schools = true` 时推荐流派都要尽量保住，写成流派名的列表（例如 `keep_schools = ["标记"]`）时只保列出的几个，`keep_schools_penalty = -60` 改这个角色的扣分，不写时用 `data/rules.toml` `[synergy] keep_schools`）；默认推荐的档位和条件规则（`[[player]]`，代码里的内部名字叫「玩家思路」，界面上不出现，显示为「筹码方案」；现在没有角色写这一层，默认推荐都按角色特性计算）；组合规则（`[[combo]]`）；队友调分（`[[teammates]]`）；队友刚需（`[[need]]`）。各节开头写有写法说明。规则可用的条件有 `maps`、`needs_owned`、`needs_source`、`without_source`、`max_round`、`exclude`、`difficulty`；`needs_source`（有这种体系的来源时才生效）、`without_source`（没有来源时才生效）写 `data/rules.toml` `[sources]` 里的名字，已持有那一项列的筹码、或自己和队友里有那一项列的角色时算有来源，两个条件成对写在同一筹码的两条规则上时任何局面恰好命中一条。扣分的特性规则、角色专属规则可写 `net`（同一筹码另一条加分规则里的同一个效果时，卡片上两条合成一个标签，写净效果）。改之前先读 `mechanics/` 里对应的机制，不要只凭效果原文推断。
- `data/series.toml`：同系列筹码的上位替代（`strict`，低一级不参与推荐度比较）和对比行的要点，以及每一对算或不算的理由。判断规矩和构建检查见「游戏改了一张筹码的效果」。
- `data/rules.toml`：各种数值参数（见「数据结构」）。全局性的改动（改了通用规则或引擎）要用同一批固定局面的基准快照横向检查全部角色：
  - 改动前 `.venv\Scripts\python -m tools.baseline record before --only engine`，改动后 `record after`，再 `compare before after --only engine`。逐条比首推、各项分值和分项、推荐度、推荐区的先后、方案模式的位次，浮点数逐位比（只差在末位的也算差异，单独列出）；有意的改动用 `--expect` 登记。影响摘要（每类局面里首推、推荐度、前三名先后变了的个数）在 `.tmp\baseline\compare-before-after-engine.md`。推荐这一个领域用的固定局面随仓库发布，不需要外部输入。

改完适配表（或改了推荐代码）以后重新生成两份审查清单：

```powershell
.venv\Scripts\python tools\make_review.py            # 两份都生成，约几分钟（横向检查那份慢）
.venv\Scripts\python tools\make_review.py --only review   # 只生成适配表审查清单，约 1 秒
.venv\Scripts\python tools\make_review.py --only audit    # 只生成横向检查
```

- 两份清单都是生成的，不要手改；改的是 `data/` 里的文件，改完重新生成。提交时看清单的差异，就知道哪些角色的排名变了。
- 清单只由文件决定：今天按 `data/meta.json` 的 `data_date` 算，限时地图按那天是否现役，哪天、在哪台电脑上生成都一样。
- 清单开头记着「生成依据」的指纹；`tools/check_data.py` 对一下就知道是不是最新的（横向检查重算要好几分钟，不用每次重算），过期了会提示重新生成。

想量「改了几个局面、首推变了几个」（比审查清单更细），用基准对比工具，见 [测试指南.md](测试指南.md) 第六节「推荐对比工具」。

## 检查与测试

```powershell
# 检查 data/ 改得对不对（改完数据跑；--add-codes 给新筹码追加编号；--format 按统一排法重排 JSON）
.venv\Scripts\python tools\check_data.py [--add-codes] [--format]
# 快测（默认）：慢测试、实机测试以外的全部测试，按模块并行，约 5 分钟（默认 8 路并行时的大约数，视电脑而定）
.venv\Scripts\python -B tools\run_tests.py
# 慢测试（名单写在 run_tests.py 里）：约 4 分钟
.venv\Scripts\python -B tools\run_tests.py --slow
# 快测 + 慢测试：约 6 分钟（不含实机测试）
.venv\Scripts\python -B tools\run_tests.py --all
# 只跑指定的模块（短名，逗号分隔）；--jobs N 改并行路数（默认 8），--list 只列出不跑
.venv\Scripts\python -B tools\run_tests.py --only test_data,test_icon
```

- `tools/check_data.py` 检查 `data/` 改得对不对：筹码名不重复、`fit`/`fit_minor` 写的是角色名、`group`/`school`/`maps` 对得上、地图直接发放的筹码有所属地图；角色名和编号不重复、四个职业权重写全、`aliases` 齐全、`group` 取六类之一；同系列筹码每两张都写了一对、每一对都写了理由；每张现役筹码都有分享编号、编号不重复、编号表里那一行的 `en` 和 `chips.json` 一致；地图的任务和四个难度的进度上限齐全、`progress_cap` 和 `progress_caps` 对得上、限时地图的日期和开关写法对、每张地图的 `file` 指向的机制文档存在且「任务」表里的任务名和这张地图的 `tasks` 一致；筹码、角色、地图、畸变组件都写了游戏繁体中文界面里的名字，繁体任务和 `tasks` 条数相同，繁体名不和同一类里别的名字、旧名撞车；`synergy.toml`、`rules.toml` 里提到的筹码名、角色名、地图名都存在；`data/` 下 JSON 的排法是统一排法（`--format` 重排）；`review/` 两份清单是最新的。哪一项错了会报出来，写明哪个文件、哪一项、怎么改；没问题时最后一行写「筹码 N、角色 N、地图 N：没发现问题」。
- `tools/run_tests.py` 每个模块一个子进程、模块之间并行；用例失败、进程中途退出或收尾时崩溃、超时都算没通过；没通过的模块的输出存在 `.tmp\test-logs\<模块>.log`。默认还查「程序用到了发行的版本里排掉的模块」。各测试文件测什么、改了哪里跑哪些、怎么看结果，详见 [测试指南.md](测试指南.md)。

## 开发工具

`tools/` 里另有八样给开发者用的工具：识别评测、截图回放、识别耗时、界面预览、文字识别比对、自编 OpenCV 比对、校准推荐、对着游戏窗口调试。它们不随发行的版本发布，只从源码运行：都在项目根目录运行，用项目的虚拟环境（下面写 `.venv\Scripts\python`），参数写在各脚本开头的说明里。它们的测试在 `tests/test_dev_tools.py`（见[测试指南](测试指南.md)）。

**识别样本**：识别评测、截图回放、识别耗时、文字识别比对、自编 OpenCV 比对和界面预览（不加 `--idle` 时）都要读仓库根目录 samples 文件夹里的游戏截图，多数还要读那里的标注（labels.json、stars_labels.json、panel_labels.json）。识别样本不随仓库发布（体积大，截图上有玩家昵称），要自己截图、写标注：放在哪里、三份标注各有哪些字段，见[测试指南](测试指南.md)第五节「识别样本怎么准备」。这几样工具读的都是 samples 文件夹（不认测试用的环境变量 `ACC_SAMPLES_DIR`；自编 OpenCV 比对可以用 `--samples` 换），缺了要用的文件时先说明缺哪个、准备方法在哪里，以退出码 2 结束。

- 工具里有几处按文件名取样本：截图回放的五段（`RUNS`）、识别耗时的四张图、界面预览各状态用的截图、各评测脚本开头列的已知读不出（`KNOWN`）和 `tools/eval_aspect.py` 的 `TASKS_OPEN`、`tools/eval_panel.py` 的 `EMPTY_PANEL`。这些是照开发时那一批截图写的，换成自己的截图时照各脚本开头的说明改这几处（对不上文件名的 `KNOWN` 不起作用，那几处照常算错）。
- 识别还要用到下载的识别图片（角色照、Q 版头像、筹码图标）：第一次运行开发版时自动下载，也可以运行 `tools/fetch_assets.py`、`tools/fetch_chip_icons.py`。
- 下面写的用时是约一百张 4K 样本时的大约数，视电脑而定，样本越多、电脑越忙越久。识别评测、回放、耗时都很占处理器，打游戏时不要跑。

### 识别评测（`tools/eval_*.py`）

拿识别样本逐张核对各项识别，并把截图缩小、加边、改成别的窗口比例再读一遍，看换了分辨率和窗口比例时读得对不对。六个脚本各管一块，`tools/eval_common.py` 是它们共用的读图、命令行参数和缺样本的说明：

- `tools/eval_vision.py`：筹码三选一（候选筹码名、稀有度、刷新次数、概率、选中项、识别的自检提示），原图、缩到 1920 宽和 1280 宽、左右加边、上下加边各一遍。要 labels.json。约 4 分钟。
- `tools/eval_hud.py`：左上角的轮次、任务栏上认地图，以及没有地图名的画面不被误认成显示地图名的加载画面。要 labels.json；另读 samples 文件夹里 extra 子文件夹下另加的截图（`EXTRA`，不写进标注，没有就跳过）。约 5～6 分钟。
- `tools/eval_hero.py`：左下角立绘认角色（被挡住的画面要认不出、不能认错）、选角界面判断。要 labels.json、panel_labels.json 和下载过的角色照。约 5～6 分钟。
- `tools/eval_stars.py`：自己的星数、玩家列表每一行的星数、队友的角色和是否电脑；`--aspect` 另加模拟的 4:3、21:9。要 stars_labels.json 和下载过的 Q 版头像。约 1～1.5 分钟。
- `tools/eval_panel.py`：「查看筹码」面板（筹码、页签、选中的页签是不是自己）；`--synth` 另把资料库里全部筹码的图标画进空面板，看每个筹码都认得对。要 panel_labels.json、labels.json 和筹码图标（`tools/fetch_chip_icons.py`）。约 1～1.5 分钟。
- `tools/eval_aspect.py`：按游戏的缩放规则把样本合成 4:3、16:10、21:9、32:9、竖长 9:16 和上下黑边、左右黑边的画面，三选一、角色、轮次、地图、任务栏、星数、队友、选角界面各读一遍。要三份标注。约 20 分钟，`--quick` 只合成其中四种。

```powershell
.venv\Scripts\python tools\eval_vision.py [--quick]          # --quick 只测原图
.venv\Scripts\python tools\eval_hud.py
.venv\Scripts\python tools\eval_hero.py
.venv\Scripts\python tools\eval_stars.py [--aspect] [-v]     # -v 打印每一行的明细
.venv\Scripts\python tools\eval_panel.py [--quick] [--synth]
.venv\Scripts\python tools\eval_aspect.py [--quick] [-v]
```

都可以加 `--limit N`（只评前 N 张，试跑用）和 `--json 路径`（每张图的读数和结果另存成 JSON，改动前后各存一份就能逐张比）。输出：每张样本一行，每个变体一个记号（✓ 对，✗ 错，· 跳过：样本本来就不比目标宽，或缩小以后窗口小于支持的下限），读错的另起一行写明读成什么、应为什么；最后是各变体的汇总和平均用时。已知读不出的（`KNOWN`，逐处写明原因）照常打印、单独列出，不算失败。都通过时退出码 0，有读错的 1，缺样本、缺筹码图标 2。不写文件（`--json` 除外），不用开游戏。

### 截图回放（`tools/replay.py`）

把一串截图按顺序交给和悬浮窗相同的识别流程（`advisor/vision/pipeline.py` 的 `FrameProcessor` 和记账的 `Session`），每张停三帧、帧与帧之间按 4 秒算，打印每一步发生了什么：认出角色、读到轮次和星数、认出地图、三选一给出推荐、记下选中的筹码、判出新的一局、对局结束。不开游戏就能检查整条链路。

```powershell
.venv\Scripts\python tools\replay.py                              # 默认回放五段，逐张核对
.venv\Scripts\python tools\replay.py 凛 截图1.png 截图2.png ...   # 起始角色（可以不写）和截图：只回放、打印，不核对
```

- 默认回放要 labels.json、stars_labels.json 和截图：按文件名里的拍摄时刻分成五段，每段新建一个记账、起始角色故意设错（看能不能自动改对），逐张核对角色、地图、新一局的判断、已有筹码和传进推荐的读数，画面上本来就看不出的列在 `KNOWN` 里。最后列出核对不上的地方，全部对上时退出码 0，否则 1。约 4 分钟。
- 回放自己的截图用第二种写法：文件名以「年月日_时分秒」开头（例如 20261002_213051_……）时，判新的一局和「同一次三选一」按拍摄时刻算；有 labels.json 时照它认哪张是三选一、三选一关了没看到选中哪个时替玩家补录，没有时按画面认、不补录。截图都先解码放在内存里（一张 4K 截图约 24 MB），张数多时分段回放。

### 识别耗时（`tools/perf.py`）

量识别各步的耗时、处理器占用和进程内存，打成四张表：① 各步单独量（预筛、三选一、读轮次和任务栏、认角色、读星数、选角界面、离开对局后的整幅识别、对局外画面的解析、算推荐）；② 按 `data/rules.toml` 的 `[watch]` 节奏，用和悬浮窗相同的识别流程把几种场景各跑 20 秒，量处理器占用、每帧间隔和各项识别做了几次；③ 战斗画面上忽然出现三选一，到给出推荐用了多久；④ 进程内存（载入识别模型、角色照、星数模板前后，再离屏建一个悬浮窗）。

```powershell
.venv\Scripts\python tools\perf.py [--quick] [--seconds 20] [--trials 8] [--unchanged-ms 毫秒] [--capture]
```

- 要识别样本里的四张 4K 截图（三选一、对局画面、任务栏开着、战斗画面；文件名写在脚本开头的 `SELECT`、`HUD`、`TASKS`、`BATTLE`，换成自己的截图时改这几个常量）。默认不截屏、不用开游戏；加 `--capture` 时另对着游戏窗口截图 30 次，量截图本身的耗时，要先开游戏。
- `--quick` 只量第 ① 项；`--unchanged-ms` 临时改「画面没变时最多隔多久重新识别一次」，比较不同取值。
- 只打印，不写文件。约 4 分钟。同一份代码几次运行之间有两三成的波动，比较改动前后要在同一时段交替跑，只看相对差别。

### 界面预览（`tools/preview_overlay.py`）

不开游戏，用一张截图走完「识别 → 记账 → 悬浮窗」，把悬浮窗画成图片，看各种状态下的界面：提示行、卡片的开合、悬停说明、「关于」和设置窗口、各套皮肤、悬浮窗放在游戏截图上默认位置的样子。默认在 Qt 的离屏平台上画，不弹窗、不出现在屏幕上，同样的参数每次画出来逐像素相同；画的是发行的版本的样子（标题栏不写「开发版」）。外观基准（`tools/baseline` 的 ui 领域）也照它的状态表画。

```powershell
.venv\Scripts\python tools\preview_overlay.py 截图.png 凛 --round 4 --star 1 --out .tmp\preview.png
.venv\Scripts\python tools\preview_overlay.py --idle --hero 美咲 --auto-hero --expanded --out .tmp\idle.png
.venv\Scripts\python tools\preview_overlay.py --all .tmp\previews       # 状态表 SCENARIOS 里的各种状态一次画完
```

- 第一个参数是三选一的截图（不写时用识别样本里的一张），第二个是角色；`--idle` 不识别截图，画还没出现三选一时的样子，不用样本。`--all` 的各状态用识别样本里的几张截图（文件名写在脚本开头）。没下载过识别图片时，筹码图标画成稀有度色圈。
- 各种状态的参数（`--expanded`、`--picked`、`--missed`、`--hover-reason`、`--settings`、`--in-game`、`--skin` 等几十个）都写在脚本开头。
- 主图存到 `--out`（默认 `.tmp\overlay_preview.png`），另存的图（悬停说明、「关于」、设置窗口、贴在游戏截图上的样子）在文件名后面加后缀；屏幕上每张图打一行事件、摘要、状态和各卡片的开合。一张几秒；`--all` 约半分钟到一分钟。

### 文字识别比对（`tools/compare_ocr_lite.py`）

拿原版 RapidOCR 和随程序的精简版 `rapidocr_lite` 对全部样本截图逐一比对：先比两边检测、方向分类、识别三个会话的选项，再比每张图整图识别的框、文字和置信度（浮点不留容差），再把每个框裁下来比「只识别不检测」。改了 `rapidocr_lite/`、升级 onnxruntime 或原版 rapidocr 以后跑，要 0 处不同。

```powershell
.venv\Scripts\python -B tools\compare_ocr_lite.py [--limit N] [--show N]
```

- 要识别样本里的截图（PNG、JPG，含子文件夹，不读标注）和装好的原版 rapidocr（`requirements.txt` 里有）。
- 输出：会话选项不同几项、比了几张图几个框、不同几处（列出前 `--show` 处）、两边整图识别的用时（只作参考），以及方向分类判成要转 180 度的框；0 处不同时退出码 0。约 6～8 分钟。

### 自编 OpenCV 比对（`tools/compare_cv.py`）

发行的版本用自编的精简 OpenCV 和不带 OpenBLAS 的 numpy（见「打包发行版」）。这个工具把同一段探针在装官方版、装自编版的两个环境里各跑一次：对每张样本截图，把项目用到的每个 cv2 函数照程序里的参数各调一遍，输出按字节比（浮点末位不同也算差异），`np.linalg` 的几个函数一起比；再核对两边构建信息里的 CPU 基线、分派、并行框架、IPP 版本和 JPEG、PNG 的 SIMD。升级 OpenCV、numpy 或改了 `tools/build_cv.py` 的编译参数以后跑。项目新用了一个 cv2 的名字时，要给探针补一个调用、写进 `COVERED_NAMES`（`tests/test_dev_tools.py` 先查出来）。

- 先建两个比对用的虚拟环境，放在仓库的 `.tmp` 下，不用开发环境 `.venv`（免得和正在跑的测试抢）：都照 `requirements.txt` 用 `--no-deps` 装，例如 `.tmp\cv-cmp-official` 照原样，`.tmp\cv-cmp-custom` 装好以后再用 `pip install --no-deps --force-reinstall` 换上 `.tmp\selfbuild\wheels` 里自编的 OpenCV 和 numpy 两个 wheel。
- 要识别样本里的截图（不读标注；`--samples 文件夹` 可以换别的截图文件夹）。

```powershell
.venv\Scripts\python tools\compare_cv.py --official .tmp\cv-cmp-official\Scripts\python.exe --custom .tmp\cv-cmp-custom\Scripts\python.exe [--baseline]
```

- 输出：按字节不同几处（写明哪个调用、哪张图）、探针没覆盖到的 cv2 名字、构建信息不一致的几项；两边的构建信息另存在 `.tmp\selfbuild` 下。没有不同、全部覆盖时退出码 0。加 `--baseline` 时两个环境各录一次识别和推荐基准（`tools/baseline` 的 vision、engine 领域）再比对，要 0 差异。
- 探针两边各跑一遍，约一百张样本要几分钟；`--baseline` 另要十几分钟。

### 校准推荐（`tools/calibrate.py`）

汇总推荐日志：推荐与实际选择的一致率（按星数、按角色）、实际选择和推荐不同的常见情形、「不认同」的原因分布和补充说明。按筹码方案推荐的三选一不计入（那是玩家自己的方案算的），按「查看筹码」面板改正的选择不计入一致率（多半是思考时间用完时游戏自动选的）；没选首推、原因点的是「想试别的玩法」的也不计入一致率和「推荐 → 实际」的对照（推荐没有问题，只是那一次想换个玩法；同一次有几条原因时以最后一条为准），汇总里另写一行有几次。什么时候校准、校准完做什么，见下一节「校准」。

```powershell
.venv\Scripts\python tools\calibrate.py                           # 汇总上次校准以来的日志
.venv\Scripts\python tools\calibrate.py --all                     # 汇总全部日志
.venv\Scripts\python tools\calibrate.py --out .tmp\calibrate.txt  # 汇总另存成文件
.venv\Scripts\python tools\calibrate.py --mark                    # 校准做完：记一条「已校准」，局数从 0 重新计
.venv\Scripts\python tools\calibrate.py --file 导出文件                       # 读校准导出文件（默认只算正式版玩家）
.venv\Scripts\python tools\calibrate.py --file 导出文件 --group formal,beta  # 正式版和测试版都算
```

- 要推荐日志：开发版每次给出推荐都记一条（`advisor/logbook.py`），在项目根目录的 logs 文件夹里，一个月一个文件；先用开发版打一些局。不用识别样本、不用开游戏。
- 汇总打在屏幕上（`--out` 另存一份）。几秒。
- 读服务器从对局报告导出的校准文件：默认只算正式版玩家，`--group formal,beta` 带上测试版（`dev` 是开发者电脑）；一次只读一个文件（局号每次导出现编，两份文件合起来读会把汇总算重）。导出里只有选了原因的「不认同」，没有补充说明，所以「不认同」的次数比本机日志里的少，「未选择原因」恒为 0。

### 对着游戏窗口调试（`tools/live.py`）

命令行版的「截图 → 识别三选一 → 给推荐」，调试识别和推荐用（平时用悬浮窗）。角色、星数、轮次、地图、已有筹码在命令行指定，三个候选筹码、剩余刷新次数和概率从画面上读，交给和悬浮窗相同的记账算推荐，按命令行推荐的写法打出来，不开悬浮窗。

```powershell
.venv\Scripts\python tools\live.py --hero 凛 --star 1 --owned 标靶      # 截一次当前的游戏画面
.venv\Scripts\python tools\live.py --hero 凛 --watch                   # 每秒截一次，出现新的三选一就给推荐（Ctrl+C 结束）
.venv\Scripts\python tools\live.py --hero 凛 --image 截图.png           # 只识别这张图片，不用开游戏
```

- 不加 `--image` 时要开着游戏：截的是屏幕上游戏窗口的那一块，游戏窗口不能最小化，被别的窗口挡住的部分也会截进来。
- 另有 `--round`、`--map`、`--source`、`--tier`（任务来源的等级）、`--interval`（`--watch` 的截图间隔，秒）。`--watch` 时和悬浮窗一样记账：三选一关闭时把选中的筹码记进已有筹码。不读写设置文件。
- 一次几秒；`--watch` 一直跑到按 Ctrl+C。

## 版本号

版本号是「主.次.修订」三段数字（例如 1.4.2），写在 `advisor/version.py` 的 `VERSION`。程序查更新时按数字逐段比大小，只认比自己新的版本；压缩包名（`ACC-<版本号>.zip`）、文件清单名、exe 的版本信息、GitHub 上的标签都跟着它。几个人同时改代码、别人复刻以后接着开发，都照下面同一套规矩。

### 什么时候改

- 平时谁都不改：写代码、修毛病、提交改动（包括别人提的改动）都不动版本号。
- 要发版时，由发版的人第一步改：先定号、改号，再打包、测试，发出去的就是测过的那个包。
- 一个号只发一次：发出去的包不再换；发出去以后发现问题，修好了用新的号另发一版（同一个版本号的包要永远相同，见「软件内更新」的「发版时放什么」）。

### 怎么定

和上一个公开发布的版本比，这一版改了什么。从上往下看，第一条对上的就是要加的那一位，只加一位，它后面的归零：

1. 有不兼容的改动：旧的设置、筹码方案读不了；系统要求提高（例如不再支持某个 Windows 版本）；改了「软件内更新」里「新旧版本之间的约定」，旧版本没法在软件里更新上来。第一位加一：1.4.2 → 2.0.0。
2. 有新功能、新的游戏资料（新角色、新地图、新筹码），或者有意改了推荐的算法。第二位加一：1.4.2 → 1.5.0。
3. 其余：修毛病、改文字、提速。第三位加一：1.4.2 → 1.4.3。

中间打过多少个测试包都不算，只看和上一个公开版本之间的改动。

### 测试包

- 发版之前给人试的包用这一版定下的号，和最后发出去的同号；试出问题修好再打，号不变。还没定号时打的包，仍是上一个公开版本的号。
- 同号的包靠打包信息区分：打包脚本把打包时间、提交号（打包时所在仓库的 git 提交）和打包时有没有未提交的改动写进发行版的 `app\build.json`；「关于」窗口「版本」一节写「打包时间：……（提交 ……）」，诊断包的 `version.txt` 里也有。正式发布的包在改动都提交以后再打，「关于」窗口里就不会出现「打包时有未提交的改动」；打包时要找得到 git，不然记不下提交号（见「打包发行版」的「打包信息」）。
- 程序查更新只认比自己新的号：装着测试包的电脑不会被提示更新到同号的正式版，要换就手动下载。

### 改号时同步的几处

- `advisor/version.py` 的 `VERSION`；
- `tests/test_release.py` 里的版本断言；
- README 第一节和 `THIRD_PARTY_NOTICES.md` 开头一句的版本号（`tests/test_project_consistency.py` 的 VersionTest 会查）；
- 使用说明的设置截图 `docs/manual/settings.png`：「启动时自动检查更新」一行的说明写着当前版本号，用 `tools/make_manual_images.py --only settings` 重画；
- 换上新版本以后提示里列的这一版的主要改动：`advisor/ui/overlay_parts/wording.py` 的 `UPDATE_NEWS_VERSION` 改成新的号，`UPDATE_NEWS` 照这一版的发布说明挑几条短的（一条一行，每条十来个字，悬浮窗上不折行），`UPDATE_NEWS_SOON` 写即将上线的（没有就写空串）。`UPDATE_NEWS_VERSION` 和 `VERSION` 对不上时只写「已更新到哪一版」那一句，不列改动，免得把上一版的改动当成这一版的写出来；新加的字照「界面文字与繁体界面」核对繁体。

压缩包名、文件清单名、exe 的版本信息由打包脚本按 `VERSION` 生成，不用手改。

### 发版的顺序

1. 定号、改号（上面几处），提交。
2. 打包、测试（见「打包发行版」）。
3. 在 GitHub 上发布这一版，再往下载镜像传（见「软件内更新」的「发版时放什么」）。标签写 `v<版本号>`（例如 v1.5.0），打在这一版代码的那次提交上；发布页面、附件名、latest.json 里都是同一个号。

## 打包发行版

用 Nuitka 编译成文件夹版（一个 exe 加所需的库，不用单文件自解压，不用 UPX），发行版里不带源码。解压出来的文件夹根目录只有一个很小的启动程序 `拾星助手.exe` 和使用说明，程序本体、运行库和数据都在 `app` 子文件夹里。


  等悬浮窗：不带参数（正常双击）时，带起之前建一个命名事件，名字放进环境变量 `ACC_READY_EVENT` 传给 `app\ACC.exe`；程序显示出悬浮窗、事件循环再转约 5 秒以后触发这个事件（和程序那一侧约好的接口，没有这个变量时程序什么都不做）。启动程序最多等 15 秒：事件触发了、到时间了，都安静地以 0 退出；`app\ACC.exe` 先结束时，退出码是 0（例如已有一个在运行，请那一个显示悬浮窗后退出）或 0xACC3（`EXIT_REPORTED`，程序自己弹过「启动失败」窗口）时安静退出，其余弹窗（标题同上）：「拾星助手启动后出错退出（错误代码 0xC000001D）：处理器不支持程序用到的指令。」，空一行接「反馈问题时请附上崩溃记录 X\.tmp\crash.txt 和同一文件夹里的错误记录 overlay_err.txt。」（X 是 `app` 文件夹的完整路径；崩溃记录由程序写，启动程序不查它在不在）；启动程序的退出码就是程序的退出码。0x80000000 起的退出码是 Windows 的异常代码（崩溃时退出码就是它），按十六进制写，原因按崩溃原因表：0xC000001D、0xC0000096「处理器不支持程序用到的指令」，0xC0000005「程序访问内存出错」，0xC0000135「缺少程序要用的文件，请把压缩包整个重新解压」，0xC0000142「程序要用的组件初始化失败」，0xC000007B「程序文件已损坏，请把压缩包整个重新解压」，0xC0000409「程序检测到严重错误后自行结束」，0xC00000FD「程序出错（栈溢出）」，0xC0000017、0xC000012D「内存不足，请关掉一些程序后再打开」，0xC0000374「程序的内存数据损坏」，其余「程序异常退出」；别的非 0 退出码（例如 1，多半是程序还没来得及弹窗就出错了）写十进制的「退出码 N」，原因「程序启动时出错，请把压缩包整个重新解压」。带参数时带起就退出，不等、不按退出码弹窗。要管理员权限、改用 `ShellExecuteExW` 启动的程序一般收不到信号：它由 Windows 的「应用程序信息」服务替启动程序起，环境变量按用户自己的那一套重新给，`ACC_READY_EVENT` 传不过去，所以这种情形下等满 15 秒或等它结束，结束了照退出码判断。

  带起之前一律（含带参数）从环境里去掉 `__COMPAT_LAYER`：给 `拾星助手.exe` 设的兼容性（例如「替代高 DPI 缩放行为」）经这个环境变量传给子进程，悬浮窗会发虚、识别会错位；直接给 `app\ACC.exe` 设的不经过这里，由程序自己检查。要等悬浮窗时，带起之前给自己加上 `SEM_FAILCRITICALERRORS`（子进程继承错误模式）：缺 DLL、程序文件损坏这类一启动就失败的情形，Windows 不再先弹它自己的错误窗口、等用户点掉，程序马上结束，只弹上面的中文说明。不加 `SEM_NOGPFAULTERRORBOX`：它让程序整个运行期间崩溃时都不经过 Windows 错误报告，事件查看器里「应用程序错误」那条记录也就没有了。

  `app\ACC.exe` 要管理员权限（有人在它的属性里勾了「以管理员身份运行」，`CreateProcessW` 报 740）时不算启动不了：改用 `ShellExecuteExW` 以 runas 启动，由 Windows 弹管理员确认框；点「是」照常运行，点「否」不启动、不弹任何提示，报别的错误时照上面按原因弹窗。测试用的启动程序（编译时定义 `ACC_LAUNCHER_TEST`，只在 `tests/test_release.py` 里编）不弹窗，提示写到标准错误输出；环境变量 `ACC_LAUNCHER_TEST_ERROR` 是十进制数时不真的启动，当作 `CreateProcessW` 报了这个错误代码；环境变量 `ACC_LAUNCHER_TEST_RUNAS` 是十进制数时当作 runas 报了这个错误代码（1223 即点了「否」）；环境变量 `ACC_LAUNCHER_TEST_WAIT_MS` 是十进制数时，等悬浮窗最多等这么多毫秒。

  C 编译器用 PyPI 的 ziglang（Nuitka 的 `--zig` 和编启动程序用的是同一个）：打包脚本把打包环境里的 ziglang 放到 `PATH` 最前；Nuitka 缓存、zig 缓存、临时文件都在 `.tmp` 下。编译和链接都按通用的 x86-64（Nuitka 只给编译加 `-march=x86_64`，链接这一步通过 `LDFLAGS` 也加上）：打包电脑支持 AVX-512 时，不加的话编出来的 `ACC.exe` 在不支持的处理器上一启动就崩、没有任何提示。编完核对 Nuitka 实际接到的这几项参数，并核对 `ACC.exe` 和启动程序里没有只有新处理器才认的指令。

## 软件内更新

发行的版本每次启动后在后台查有没有新版本；玩家点「更新」后在后台下载、核对、解压备好，备好以后在对局外自动重启，由新版本把旧版本换掉（上次已备好、还没换上的那一版，玩家点「重启更新」或下次启动时换），换上的新版本起不来就自动退回旧版本。开发版（从源码运行）不查、不下、不换，设置窗口的「检查更新」点了只说一句开发版不检查更新。

代码分四处，各模块开头的说明写得最全，改之前先读：

- `advisor/update.py`：查（`check`）、开始下载之前的检查（`preflight`）、下载整包（`download`）、解压备好（`prepare`），以及先试按文件下载、走不通再下整包的 `obtain`；
- `advisor/update_files.py`：按文件下载的核心（文件清单 `build_manifest`、`parse_manifest`，拼出新版本 `assemble`），本身不联网，按字节段取发行包的函数由调用方给；
- `advisor/update_apply.py`：换版本程序（`apply_main`），和新旧版本调用的 `pending`、`launch`、`take_result`、`after_start`；
- `advisor/update_log.py`：查更新、下载、换版本共用的记录（`app\logs\update.log`）：追加、上限和裁剪、整份重写用的锁；
- `advisor/ui/overlay_parts/updates.py`：悬浮窗这一边（`UpdateControl`：自动检查、提示行的按钮、设置窗口「启动时自动检查更新」那一行），提示的文字在同一文件夹的 `wording.py`。

### 全过程

1. 查：
   - 设置里的自动检查（`update_auto`，默认开）开着时，每次启动、悬浮窗出来约 15 秒后在后台查一次（一天里接连发了两个版本也不会漏掉后一个）；查不到不出声，这次运行不再自动查。每次查的时间和结果记在 `update.log` 里（见下面「更新记录」），设置文件不记上一次查的日期（旧设置文件里的 `update_checked` 读的时候忽略，下次保存设置时就没有了）。设置窗口的「检查更新」随时查，跳过的版本（`update_skipped`）照样提示。
   - `check` 先问下载镜像的 latest.json，再问 GitHub 上源代码地址那个仓库的 releases/latest（只返回正式版），各约 15 秒超时。源代码地址不是官方仓库时（复刻的版本）不问镜像、只问 GitHub，见「复刻以后发布自己的版本」。能拿到 GitHub 的那一版时以它为准：镜像的版本号、大小、SHA-256 都和它一样，才用镜像的下载地址（排在 GitHub 前面）、改动说明、资料同步日期和 auto；对不上时只认 GitHub 的（只从 GitHub 下载，没有改动说明）。GitHub 的附件没有 digest 时，版本号和大小都和镜像一样才用镜像的 SHA-256，否则这一版不认（下到的包没法核对）。这样下载镜像的上传令牌万一泄露、镜像上的包被换掉，能连上 GitHub 的程序也不会装上它。GitHub 拿不到时认镜像的；镜像连不上（例如域名、存储桶出了问题）时只认 GitHub 的，照样能更新。比当前版本新、又不是跳过的版本才算有新版本。
   - 联网一律经 `advisor/winhttp.py` 的 `Session`（系统的证书和代理，https 不降成 http，cookie 不收不带）。请求只带 User-Agent `AstralChipCompass/<版本号> (+<源代码地址>)`，问 GitHub 时另带 `Accept: application/vnd.github+json` 和 `X-GitHub-Api-Version` 两个头，不带别的识别信息。
   - 提示行只在对局外显示，对局中先攒着（`Overlay._playing`；中途退出一局的见「中途退出一局」那一条）；下载在后台照常进行。纯文字的提示行用 `factory.WrapLabel` 换行（名称、术语、常用双字词不从中间拆开，带链接的照旧由 Qt 断行）；「拾星助手」和「有新版本」句尾的「下好后自动重启换上」也整体不拆（`text.TIP_TERMS`），窄的皮肤上不排成「拾 / 星助手」，末行也不只剩「上。」。
2. 下载和备好（点「更新」以后，在后台线程里；下面「根」指解压出来的程序文件夹，`paths.program_folder()`）：
   - `preflight`：在根下试写 update 文件夹，所在盘剩余空间不到 800 MB（`FREE_SPACE`）时不下，写明原因。
   - 这一版有文件清单时先按文件下载：下清单，核对大小和 SHA-256；和本机现有的文件逐个比对，没变的从本机复制，变了的从发行包里按 HTTP Range 只取那几个文件，拼进 `update\new.part`，每个文件核对 SHA-256。清单下不到或对不上、服务器不支持按段取、要取的超过整包的六成、拼出来核对不上时，删掉 new.part、写一条错误记录，改下整包，不提示玩家。
   - 下整包：按下载地址的先后下到 `update\ACC-X.Y.Z.zip.part`，大小和 SHA-256 都对上、刷盘以后才改名成 `ACC-X.Y.Z.zip`，对不上就换下一个地址；再解压到 new.part（先逐项核对名字、个数、大小、压缩方式），核对 `app\ACC.exe` 的文件版本号等于新版本号。
   - new.part 改名成 `update\new`，最后写 `ready.json`：有它才算备好。出错时删掉 new.part，update 以外的东西一概不碰。
3. 换上：
   - 点了「更新」、这次运行里备好的：在对局外自动重启。备好时（或者之后每次刷新提示行时）各张悬浮窗的这一局都已经结束（`Overlay._unfinished`：进了对局、这一局没认出结束、游戏窗口也没关就算没结束；和提示行用的 `_playing` 不同，连着一阵子看不到对局读数（`game_quiet`，见「中途退出一局」那一条）不算结束：对局中按 Esc 停在菜单上、战斗画面很长时提示行照常显示，但不重启，免得在对局中途重启、丢掉这一局记的状态。每张悬浮窗刷新时记下 `last_unfinished`，两个客户端同时识别时两张的这一局都要结束；那一轮取快照读出了错的——`view.read_error` 不空，或整块出错、按默认快照画的——也按没结束算，见 `Overlay._lanes_playing`，只管自动重启，提示行显示不显示照旧），而且没开着拾星助手的其他窗口（`Overlay._other_windows_open`：程序自己的、看得见的顶层窗口里，除悬浮窗本身、工具提示、菜单和下拉列表、不接收焦点的小提示框以外都算，最小化的也算；按窗口的种类认，不认名字，以后加的窗口不用另外登记），提示行换成「马上重启换上」，排一个约 3 秒的定时器（`RESTART_NOTICE_MS`），让玩家看到这一句再关；到点时状态没变过、这一局仍然都结束着、仍然没开着其他窗口，才走下面「重启更新」那条路，否则接着等。这一局还没结束时提示行（显示的话）和设置窗口那一行写「对局结束后自动重启换上」。开着其他窗口时提示行和设置窗口那一行写「关掉拾星助手的其他窗口后自动重启换上」（这一局还没结束时照旧写等对局结束；设置窗口自己就算其他窗口），每秒看一次关掉了没有（`WINDOWS_POLL_MS`：窗口关掉时悬浮窗不一定刷新），都关掉了刷新一次、照常排上。只排定时器、不在刷新提示行的途中退出。查对局状态、查开着哪些窗口出错时按不能重启算（不自动重启，各记一条错误记录）。点了「停止」马上不再自动重启（下载线程恰好在这之前备好的，要玩家点「重启更新」）；换版本程序起来以后不再排、不再起第二次（`launched`）。
   - 自动重启时悬浮窗收在托盘里：起换版本程序之前写记号 `update\tray.json`（`advisor/ui/hidden_start.py`：格式号、要换上的版本、换之前的版本、写的时间、收着的几张 `primary`／`secondary`，两张各按自己藏没藏着算），起不来时删掉；没有收着的、手动点「重启更新」的不写。新版本的 `run()` 查过防多开以后、`hand_over_update` 以前读走（读了就删，比新版本起来以后的收尾删 `update` 早），版本就是正在运行的这一版、写了不到 10 分钟（`TTL_S`）才认：接线时不显示这几张（`Lanes` 的 `hidden`），托盘图标建出来以后照旧收着，什么都不弹；托盘图标建不出来时照常显示（`Lanes.finish_hidden_start`），不会既没有悬浮窗又没有托盘图标。新版本起不来、退回旧版本时版本对不上，旧版本照常显示。「已更新到 x」那一条照旧留到玩家关掉，从托盘打开悬浮窗时才看得到。记号的文件名、位置、格式和换版本的那几样约定一样只许加不许改；不认识记号的旧版本（1.0.0）不写，1.0.0 更新到 1.1.0 时照常显示。
   - 点「重启更新」（上次已备好、还没换上的那一版，检查时直接是备好了的；这次运行里玩家没点过「更新」，不自动重启）：`launch` 起换版本程序 `update\new\app\ACC.exe --apply-update <自己的进程号>`，等它回话说已经接手（最多 30 秒）以后照常退出；起不来、一直不回话时照常运行，这一次记成没换上。自动重启走的也是这一步，起不来时的提示一样。
   - 没换上（不点、自动重启没起来）：下次启动时，`advisor/ui/__init__.py` 的 `run()` 查过防多开以后（`hand_over_update`）调用 `pending`，有备好、该换的版本就 `launch`，起来了就以退出码 0 退出（根目录的启动程序看到 0 安静退出）。
   - 换版本程序（`apply_main`）：核对自己 → 先写一份「没做完」的结果 → 等旧进程退出（最多 30 秒）→ 把 `update\new\app` 复制成 `app.next` → 改名两次（`app` → `app.old`，`app.next` → `app`）→ 把 `app.old` 里的用户数据（`paths.USER_DATA_NAMES`）搬进新的 app（同一个盘上改名，不复制）→ 换根目录的 `拾星助手.exe`、`使用说明.html`（旧的改名成 `.old`）→ 结果写成 ok，起新的 `app\ACC.exe`，等它的悬浮窗出来（最多 60 秒，等满了它还在运行也算换好了）。
     - 新版本在悬浮窗出来之前就结束了：退回（app 改名成 `app.failed`，`app.old` 改回 app，用户数据搬回来，根目录两个文件换回旧的），结果写成 rolled_back，起旧版本。
     - 旧版本一直不退出：什么都不改，结果写成 not_applied 就退出（旧版本还开着）。改名时有文件被占着（隔一会儿再试，最多 10 秒）、复制出错等：退回原样，结果写成 not_applied，起旧版本。
     - 两次改名都做完以后换版本程序中途退出了（断电、被结束）：app 里已经是新版本，新版本收尾时把 `app.old` 里的用户数据补搬过来，结果改成 ok。
   - 要守的两条：用户数据一条都不能丢；任何时候 app 都是一个能启动的版本。每一步写一行进 `update\apply.log`。
4. 换上以后：
   - 新版本（退回时是旧版本）的悬浮窗出来以后，`take_result` 读走结果，同一个结果只交一次：ok 时说一句已更新到哪一版，换上的正是 `wording.py` 里 `UPDATE_NEWS_VERSION` 那一版时，下面列出这一版的主要改动（`UPDATE_NEWS`、`UPDATE_NEWS_SOON`，见「版本号」）；rolled_back 时把这一版记进跳过、提示新版本启动失败；not_applied 时提示没换上，下次启动再换，同一个版本两次没换上（`MAX_FAILED`）以后同样记进跳过、不再自动换（设置窗口的「检查更新」照样能查到、能再试）。
   - 后台 `after_start` 收尾：等换版本程序退出，把 `update\apply.log` 接到 `app\logs\update.log` 后面（超过 256 KB 时只留后一半，诊断包带上它），删掉 update、`app.next`、`app.old` 和根目录的 `.old`、`.new`，`app.failed` 只留最近一份。没换上、还能再换的 update 留着，下次启动再换；删不掉的下次启动再删。`update.log` 里还有查更新、下载两段（见下面「更新记录」）。

相关测试：test_update、test_update_obtain、test_update_files、test_update_apply、test_update_ui、test_upload_r2、test_update_flow（都不联网：用假的会话，或本机 127.0.0.1 上的假服务）。test_update_flow 从打包、上传脚本生成的发行包、文件清单和 latest.json 起，用真的模块走一遍查、下、备好（有清单只下变了的、镜像不认按段取时换 GitHub 的地址、没有清单下整包、改下整包、停止、出错），核对界面上的样子；另走一遍复刻的版本（源代码地址不是官方仓库：只问 GitHub，镜像一次都不碰）。

### 更新记录

查更新、下载、换版本都往程序目录的 `logs\update.log` 追加，格式是 `[YYYY-MM-DD HH:MM:SS] 谁：内容`，「谁」是「查更新」「下载」「换版本」「收尾」这类；多行的后几行缩进，程序目录里的完整路径换成 `%程序目录%`（先换它：程序文件夹多半就在用户目录里），别处的用户目录、账户名换成占位，IP 形状的主机名写成「其他地址」（程序文件的四段版本号照写）。写的时候最多 256 KB（`update_log.KEPT_LOG_MAX`），超过只留最后约一半、从一行的开头起。

- 查更新：每次自动检查、手动「检查更新」都记，没有新版本也记一行；至少写清自动还是手动、当前版本、下载镜像和 GitHub 各回了哪个版本或为什么没拿到（`_why` 的简短说法）、认下哪一版（两边一致、只拿到一边、两边对不上只认 GitHub），以及是有了新版本、比当前旧还是被跳过。
- 下载：点「更新」以后记这次是差分还是整包、要下多少字节；每个地址实际下了多少、用了多久、为什么没成；差分走不通改下整包的原因；核对、解压的结果，最后是「已备好」还是失败（失败原因）；下载前检查（空间、写不写得进）没过也记。
- 换版本：换版本程序的每一步（`update\apply.log`），收尾时接到同一个 `update.log` 后面。

追加（查更新、下载）和收尾时整份重写（换版本）共用 `advisor/update_log.py` 的进程内锁，同时写时不丢行。写记录失败（磁盘满、文件被占、没有 logs 文件夹）一律吞掉，不影响查更新和下载；开发版不查、不下，没有这份记录。诊断包带上 `update.log`，其中文字再过一遍 `paths.scrub_paths`。

### 新旧版本之间的约定

已经发出去的版本照下面这些调用、照这些读，**只能加，不能改**：要变时加新的字段、新的文件，原来的照留。改了名字或格式，已经发出去的版本就查不到新版本或换不上。

- 换版本程序的命令行：`<根>\update\new\app\ACC.exe --apply-update <旧进程号>`（也认 `--apply-update=<旧进程号>`）。发行版入口 `packaging/chip_advisor.py` 的 `main()` 一开头接住，交给 `update_apply.apply_main`，以它的返回值退出：不开崩溃记录、不导入界面库和识别库、不查防多开。
- 退出码：`apply_main` 换上了、没换上、退回了都返回 0（结果看 result.json）；没动手就退出的返回 0xACD1（参数不对或核对没通过，什么都没改）、0xACD2（另一个换版本程序正在换这个根）、0xACD3（拿不了换版本的锁，或「没做完」的结果写不进）；入口导入 `update_apply` 就出错时以 1 退出。`launch` 只有遇到 0xACD2 不记成没换上，别的没回话就结束的都记一次没换上。
- 环境变量：
  - `ACC_UPDATE_STARTED`：`launch` 建的命名事件的名字，换版本程序接手以后触发它，并从自己的环境里去掉（起的子进程不继承）；
  - `ACC_READY_EVENT`：根目录的启动程序（`packaging/launcher.c`）和换版本程序起 `app\ACC.exe` 时给的「悬浮窗出来了」事件，程序显示出悬浮窗、事件循环再转约 5 秒以后触发（`advisor/ui/startup.py`）；
  - 起新版本、旧版本时从环境里去掉 `__COMPAT_LAYER`（同启动程序）。
- 命名对象：换版本的锁是命名互斥体 `Local\AstralChipCompass.Update.<根的完整路径（不分大小写）的 SHA-256 前 16 位十六进制>`，同一个根同时只有一个换版本程序；事件名是 `Local\AstralChipCompass.<用途>.<进程号>.<随机数>`；新版本以退出码 0 结束、防多开的锁（`Local\AstralChipCompass.Overlay`）又在别的拾星助手手里时，不算起不来。
- 文件夹布局：

  ```text
  <根>\                        解压出来的 AstralChipCompass 文件夹
    拾星助手.exe  使用说明.html    根目录的两个文件，和程序一起换
    app\                       当前版本（程序目录），永远不删
    update\                    更新的工作文件夹：只有更新的代码会建、会删
      ACC-X.Y.Z.zip.part       下载中
      ACC-X.Y.Z.zip            下好、核对过（解压以后删掉）
      new.part\                解压中、拼的过程中
      new\                     解压好、核对过：压缩包里 AstralChipCompass/ 下面的东西（拾星助手.exe、使用说明.html、app\…）
      ready.json               「已备好」记号，最后写
      result.json              换版本程序写的结果
      apply.log                换版本每一步的记录（追加；收尾时接到 app\logs\update.log 后面）
    app.next\  app.old\  app.failed\         换版本过程中才有：复制出来的新版本、换下来的旧版本、起不来被退回的新版本
    拾星助手.exe.old  使用说明.html.old        换下来的根目录文件（换的过程中另有「原名.new」）
  ```

- 能删的名字：只删根下这几个——update（收尾时）；app.next、app.old、app.failed 和它们另起名的「名字-时间」（时间写成「年月日-时分秒」，即 YYYYMMDD-HHMMSS，重名时再接 -2、-3）；根目录两个文件的 .old 和 .new（正式的名字空着时不删：先把 .old 改回正式的名字，改不回就都留着）。app.next、app.old、app.failed 里还有 `paths.USER_DATA_NAMES` 列的用户数据时（只剩空文件夹的不算）留着、记一笔；目录链接只删链接本身；app 永远不删。
- ready.json（`advisor/update.py` 写，`update_apply` 读）：`{"format": 1, "version": "1.0.1", "sha256": "…", "prepared": "…"}`。version 是「数字.数字.数字」，sha256 是这一版发行包的 SHA-256（64 位小写十六进制），prepared 是备好时的本地时间；四项都对才算备好。
- result.json（换版本程序写，新旧版本读）：`{"format": 1, "status": "ok", "version": "1.0.1", "from": "1.0.0", "reason": "", "time": "…", "pid": 12345, "attempts": 0, "done": true}`。status 是 ok、rolled_back、not_applied 之一；reason 是给用户看的白话原因，只写原因、不写「这次没有换」「已退回旧版本」这类结论（旧版本的提示行先写结论，原因跟在后面另起一句「原因：……。」；不含路径，ok 时为空）；from 是旧版本的版本号（读不出时为空）；pid 是写它的换版本程序的进程号（收尾时等它退出）；attempts 是同一个版本没换上几次（not_applied 时加一，到 2 次不再自动换）；done 为 false 的是换版本程序动手之前先写的「没做完」那一份（中途被结束时它就是结果）。`take_result` 读走以后加上 `"taken": true`。读的时候 format、status、version、pid、attempts 要齐全、类型对，from、reason、time 缺了当空。
- latest.json（下载镜像上，程序查更新先读它）：

  ```json
  {
    "format": 1,
    "version": "1.0.1",
    "zip": "releases/ACC-1.0.1.zip",
    "size": 89001969,
    "sha256": "64 位小写十六进制",
    "page": "https://github.com/s1nan-dev/astral-chip-compass/releases/tag/v1.0.1",
    "notes": "https://dl.astral-chip-compass.com/notes/1.0.1.txt",
    "data_date": "YYYY-MM-DD",
    "auto": true,
    "files": "releases/ACC-1.0.1.files.json",
    "files_size": 12345,
    "files_sha256": "64 位小写十六进制"
  }
  ```

  - 必填 format（只认 1）、version（数字.数字.数字）、zip（正好是 releases/ACC-<版本号>.zip）、size（1 MiB～1 GiB）、sha256（64 位小写十六进制）、page（在 `https://github.com/s1nan-dev/astral-chip-compass/` 下面）、auto（false 时这一版只提示、引导手动下载）：缺一项、类型不对、不合要求，整份不认，记一条错误记录。
  - 选填 notes（在 `https://dl.astral-chip-compass.com/` 下面，不是时当没有）、data_date（YYYY-MM-DD 的日期，不是时当没有）。files（正好是 releases/ACC-<版本号>.files.json）、files_size（1 B～16 MB）、files_sha256 三项说的是文件清单，有一项不对就当这一版没有清单（只能下整包），别的照常认。
  - 不认识的字段一律不管：以后要加东西就加字段，format 不改（改了的话，已经发出去的版本整份不认）。
- 文件清单 ACC-X.Y.Z.files.json（打包时和发行包一起生成，放在它旁边；`advisor/update_files.py` 的 `build_manifest`）：

  ```json
  {"format": 1, "version": "1.0.1", "zip": "ACC-1.0.1.zip", "zip_size": 89001969, "zip_sha256": "…",
   "files": [{"path": "app/ACC.exe", "size": 37748736, "sha256": "…"}, …], "dirs": []}
  ```

  path 是压缩包里 AstralChipCompass/ 下面的相对路径（正斜杠），files 按 path 排序，dirs 是压缩包里有目录项、下面却没有文件的空目录（一般没有）。写法固定（UTF-8、中文不转义、键排序、LF 换行和结尾），同一个包生成两次字节一样。version、zip、zip_size、zip_sha256 要和认下的那一版一致；路径里不能有「.」「..」段、绝对路径、盘符、冒号、反斜杠、空段，不分大小写不能重名；文件数、空目录数各不超过 20000，解压后合计不超过 2 GiB，清单本身不超过 16 MiB；必须有 app/ACC.exe 和 拾星助手.exe。有一条不对就不走按文件下载。发行包里的中央目录、本地文件头只用来定位，写到哪里、写多大、内容对不对都以清单为准。
- GitHub（源代码地址那个仓库的 releases/latest）：用到 tag_name（`v<版本号>`）、html_url（在源代码地址下面），附件 ACC-<版本号>.zip 的 size、browser_download_url（在源代码地址的 `/releases/download/` 下面，官方版即 `https://github.com/s1nan-dev/astral-chip-compass/releases/download/`）、digest（`sha256:<十六进制>`，GitHub 自己算的），附件 ACC-<版本号>.files.json 的 digest 就是清单的 SHA-256。404（仓库是私有的、删了、没有正式版）、403 和 429（限流）、5xx、超时、格式不对，都当 GitHub 这边没拿到。
- 程序只在浏览器里打开发布页面（源代码地址下面）和下载镜像下面的地址（复刻的版本不用镜像，只有发布页面：「手动下载」打开认下那一版的发布页面，没有认下的版本时打开 `<源代码地址>/releases`），也只从这两处和 GitHub 的附件地址下载；地址里不能有空白、反斜杠，路径里不能有「.」「..」段（含转义的写法）。版本文件万一被人改了，也不会把人引到别处。

### 发版时放什么

先在 GitHub 上发布这一版，再往下载镜像传（latest.json 最后传：中途哪一步失败，程序查到的都还是原来那一版）。

- GitHub 发布页面：标签 `v<版本号>`，发成正式版（releases/latest 只返回正式版，标成预发布的程序查不到），附件两个：
  - `ACC-<版本号>.zip`：打包产出的发行包；
  - `ACC-<版本号>.files.json`：打包时在发行包旁边生成的文件清单。发布说明的「下载和使用」里给它单独写一段、整句加粗：「**下面的 `ACC-<版本号>.files.json` 是程序更新用的文件清单，不用下载。**」附件列表里清单和发行包挨着，不加粗容易被当成要下的文件。少了这个附件，能连上 GitHub 的程序这一版就只能下整包（清单可信靠的是 GitHub 给附件算的 digest）。
- 下载镜像（Cloudflare R2，存储桶 acc-update，公开地址 https://dl.astral-chip-compass.com/ ），由 `tools/upload_r2.py` 传：
  - `releases/ACC-<版本号>.zip`：缓存一年（immutable），同一个版本号的包永远不变；
  - `releases/ACC-<版本号>.files.json`：缓存同发行包；
  - `ACC-latest.zip`：最新那一版的副本，缓存 5 分钟，下载时存成 ACC-<版本号>.zip。使用说明和程序里的「手动下载」给的都是它，名字不能改；
  - `notes/<版本号>.txt`：这一版改了什么（UTF-8 纯文本），提示行的「看看改了什么」打开它；
  - `latest.json`：不缓存，最后传。
- 发行包和清单发出去以后不再改：同一个版本号要换包时另发一个版本号。正在按字节段取旧包的程序会拼出对不上的文件，核对不过才改下整包，白下一遍。

上传脚本 `tools/upload_r2.py` 的用法（在项目根目录下，GitHub 上发布了这一版以后）：

```powershell
.venv\Scripts\python tools\upload_r2.py --notes 说明.txt --dry-run   # 先试运行：核对 GitHub、列出要传的东西，不连 R2
.venv\Scripts\python tools\upload_r2.py --notes 说明.txt             # 真传
```

- 参数：`--zip`（发行包，默认 `dist\ACC-<版本号>.zip`，版本号取 `advisor/version.py`）；`--files-manifest`（文件清单，默认发行包旁边的 ACC-<版本号>.files.json，要和发行包是同一次打包生成的，对不上就停）；`--notes`（这一版改了什么，不带时不传，latest.json 里也不写 notes）；`--no-auto`（latest.json 的 auto 写 false：程序只提示有新版本、引导手动下载）；`--skip-github-check`（不核对 GitHub，打一行警告）；`--dry-run`（只算、只打要做的事，不连 R2；照样读令牌文件、核对 GitHub）；`--public-base`、`--github-api` 只给测试用（指到本机的假服务）。
- 令牌文件用 `--token-file` 给，不给时取环境变量 `ACC_R2_TOKEN_FILE`；格式是 UTF-8 的三行「名字=值」（access_key_id、secret_access_key、endpoint）。脚本不打印令牌，报错里遇到就换成占位。令牌泄露以后别人能换掉镜像上的包和 latest.json：能连上 GitHub 的程序以 GitHub 上的 SHA-256 为准、不会装上，连不上 GitHub 的就只能信镜像，所以令牌文件不进仓库、不发给别人，泄露了马上在 Cloudflare 删掉旧令牌、建新的。
- 顺序：核对 GitHub 上最新的正式版就是这一版、两个附件的 digest 等于本地发行包和清单的 SHA-256（对不上就停）→ 传 `releases/ACC-<版本号>.zip` → 从公开地址下回来，核对大小和 SHA-256 → 传 `releases/ACC-<版本号>.files.json` → 从公开地址读回清单，核对大小和 SHA-256 → 传 `ACC-latest.zip` → 传 `notes/<版本号>.txt`（带 `--notes` 时）→ 传 latest.json（写上清单的三个字段）→ 从公开地址读回 latest.json 核对；最后用公开地址按字节段取一次发行包的前 1 KB，核对回 206、Content-Range 和长度（不对时只打一行警告：程序见到不支持按段取会改下整包）。
- 退出码：0 完成（试运行：没发现问题）；1 停下了，R2 上什么都没动（含参数写错）；2 停下了，R2 上已经动了一部分（输出里写明停在哪一步、哪些传上去了）。同一版重新运行没有副作用：每个文件都是整个覆盖。

## 使用说明网页版

发行版里的「使用说明.html」同时发布到 GitHub Pages：https://s1nan-dev.github.io/astral-chip-compass/ 。`docs/使用说明.md` 仍是唯一要改的原稿；网页和发行版里的那一份逐字节相同，两边都调用 `tools/manual_html.py` 的 `build_page`（只用标准库，GitHub 的机器上不用装 PySide6、numpy 等本项目的依赖）。

- 自动发布：推送到 `main`、改到 `docs` 下的 `.md`（含 `docs/使用说明.md`；按通配写，不靠路径过滤认中文文件名，改到别的说明时多发布一次，网页不变）、`docs/manual/` 下的截图、首页 `README.md`、`tools/manual_html.py`、`advisor/version.py`（版本号）、`data/meta.json`（资料同步日期）或 `.github/workflows/manual-pages.yml` 时，仓库的 `.github/workflows/manual-pages.yml` 重新生成网页并发布；也可以在 Actions 页面手动运行「使用说明网页版」。只在 `s1nan-dev/astral-chip-compass` 里发布，复刻的仓库和其他副本里跳过（那里没有打开 GitHub Pages）；仓库还是私有的时候也跳过。
- 在本机生成预览：`.venv\Scripts\python -B tools\manual_html.py --out .tmp\使用说明.html`，用浏览器打开 `.tmp\使用说明.html`。没有第三方包的 Python 3.14 也能运行；`build_release.py --manual 路径` 生成的也是同一份。
- 第一次发布前在仓库的 Settings → Pages 把「Build and deployment」的「Source」选成「GitHub Actions」。仓库公开、打开 Pages 以前推送的，那次运行跳过了，在 Actions 页面手动运行一次「使用说明网页版」就发布了。

## 复刻以后发布自己的版本

拾星助手按 AGPL-3.0 授权，可以复刻（fork）以后修改、发布自己的版本；分发时要附上完整的源代码、保留版权和许可证声明，具体以许可证全文为准。

### 必须改：源代码地址

把 `advisor/version.py` 的 `SOURCE_URL` 换成自己的仓库地址，照 GitHub 上显示的原样写成 `https://github.com/<用户名>/<仓库名>`：用户名、仓库名的大小写和 GitHub 上一致，末尾不带斜杠、不带 `.git`。写法不对时程序推不出查更新的地址，不查 GitHub；用户名、仓库名的大小写和 GitHub 上不一致时查得到，却因为发布页面的地址对不上而不认。源代码地址决定这几样：

- 「关于」窗口「许可证」一节写的源代码地址；
- 软件内更新查哪里：查这个仓库最新的正式版（`https://api.github.com/repos/<用户名>/<仓库名>/releases/latest`），只认这个仓库发布页面上的附件，「看看改了什么」「手动下载」打开的也是它的发布页面；
- 用不用官方的下载镜像：镜像（`dl.astral-chip-compass.com`）上只放官方发布的版本，`SOURCE_URL` 不是官方仓库时程序不查、不下它（`advisor/update.py` 的 `MIRROR_SOURCE`）。

这样改版的用户不会被提示换成官方版，只会收到改版自己发布的新版本。源代码地址不在 GitHub 上时，软件内更新没有地方可查：不联网，设置窗口的「检查更新」说「这个版本没有设置查更新的地址」（`advisor/update.py` 的 `NO_SOURCE`），要用就得改 `advisor/update.py`。

对局报告也按源代码地址判断：`SOURCE_URL` 不是官方仓库时只存不发（`advisor/game_report.py` 的 `target`，判断同 `update.USE_MIRROR`），改过的程序不往官方地址发，也不混进统计；设置里的开关照旧有效。

### 改了源代码地址以后的测试

改完跑一遍和源代码地址有关的测试：`.venv\Scripts\python -B tools\run_tests.py --only test_update,test_update_flow,test_update_ui,test_upload_r2,test_release,test_manual_html`。下面这几组是照官方版写的，只改了源代码地址就会有一百多条不过（多半在 `tests/test_update.py`），要跟着改；别的测试文件不用源代码地址。

- 查更新（`tests/test_update.py`、`tests/test_update_flow.py`，`tests/test_update_ui.py` 有一条）：测的是官方版的查法，源代码地址就是下载镜像上那个仓库、先问镜像，样本回话里写的也是官方仓库的地址。查法本身改版用不着动，可以在这几组测试开头把由源代码地址算出的几个常量（`advisor/update.py` 的 `USE_MIRROR`、`GITHUB_API`、`PAGE_PREFIX`、`DOWNLOAD_PREFIX`）换回官方的再测，`tests/test_update.py` 的 `as_fork` 传官方的地址就是这样换的。复刻版本自己的查法（只问 GitHub、不碰镜像）由 `tests/test_update.py` 的 `ForkCheckTest` 和 `tests/test_update_flow.py` 里复刻的那一趟核对，不用另写。
- 往下载镜像传（`tests/test_upload_r2.py`）：上传脚本往官方的镜像传，测试核对它查的 GitHub 接口、传的版本和程序是同一个仓库，`latest.json` 里的发布页面地址也照官方仓库核对。不架自己的镜像就用不上这个脚本；架了的，照下面「发布自己的版本」换掉地址，测试里的样本地址跟着换。
- 声明文字（`tests/test_release.py` 的 `VersionTest`）：「免费软件」声明是写死的原文，测试逐字核对它和源代码地址；「许可证」一节和免责声明的「获取渠道」由源代码地址拼出来，测试核对 `THIRD_PARTY_NOTICES.md` 第四、五节和 `docs/使用说明.md`「声明」一节里同样的文字，这几处要一起改（见下面「建议一并改」）。
- 使用说明网页版（`tests/test_manual_html.py`）：首页、`CONTRIBUTING.md` 和 `.github` 下的表单里指向网页版的链接，`.github/workflows/manual-pages.yml` 只在哪个仓库发布，都按源代码地址核对。

照上面改了文字和链接以后，逐字核对旧文字的测试也要跟着改，例如 `tests/test_project_consistency.py` 里核对首页链接的那一条。

### 发布自己的版本

- 版本号照「版本号」一节自己往下排，从复刻时的号接着加；和官方的号互不相干（两边的程序只查各自的仓库）。
- 在 GitHub 上发成正式版（标成预发布的程序查不到），标签 `v<版本号>`，附件照「软件内更新」的「发版时放什么」：`ACC-<版本号>.zip`（程序用 GitHub 给附件算的 SHA-256 核对它）和打包时生成的 `ACC-<版本号>.files.json`（不放也行，程序就只下整包）。不需要下载镜像。
- 想架自己的下载镜像：把 `advisor/update.py` 的 `MIRROR_BASE`、`MIRROR_SOURCE` 换成自己的地址和仓库，`tools/upload_r2.py` 的 `PUBLIC_BASE`、存储桶和 `GITHUB_API`（程序由源代码地址推出的那个 GitHub 接口，`tests/test_upload_r2.py` 核对两边一样）也换成自己的。
- 「关于」窗口和诊断包里的打包时间、提交号是打包时所在仓库的（见「版本号」的「测试包」），用户反馈问题时用得上。

### 建议一并改

## 校准

- 悬浮窗每次给出推荐都记一条完整记录到 `logs\YYYY-MM.jsonl`（对局状态、推荐全文、实际选择、「不认同」的原因和说明）。自上次校准起满 20 局（`data/rules.toml` 的 `[watch] calibrate_games`）时，开发版的悬浮窗提示「推荐日志已满 20 局，可以校准」；发行的版本不带校准工具（`tools/calibrate.py` 只从源码运行），不显示这条提示。同时识别两个客户端时推荐日志一张悬浮窗一条线，第二张的记录另带 `lane`、三选一编号带「线名-」前缀；只开一个客户端时记录都不带 `lane`、编号不加前缀。两个客户端的局都算进「满 20 局」，提示只在第一张悬浮窗上出。
- 校准时运行 `.venv\Scripts\python tools\calibrate.py`，汇总自上次校准以来的日志：推荐与实际选择的一致率（按星数、按角色）、实际选择与推荐不同的常见情形、「不认同」的原因分布和补充说明。据此调整 `data/rules.toml` 的数值参数或 `data/synergy.toml` 的规则，跑相关测试和基准对比（见「推荐规则与审查」），再运行 `.venv\Scripts\python tools\calibrate.py --mark`，把校准计数从 0 重新开始（工具的用法见「开发工具」）。

## 两个客户端同时识别

设置窗口的「游戏平台」选「Steam端+TapTap端」（`capture.BOTH`）时，Steam 版和 TapTap 版各跑一路识别、各一张悬浮窗。这一节记两张悬浮窗怎么接线（新模块、只有一份的部件、设置和方案同步、热键、关闭和退出、性能测试）、两路识别共用的几块（设置文件的分栏、换端、两把锁）和这样做出来的限制。

- 两张的接线和增减：`advisor/ui/overlay_parts/lanes.py` 的 `Lanes` 管两张的窗口、Session、识别线程、跟随、热键合并、增减和退出收尾；`Lane` 是一张的那一套（窗口、Session、识别线程、跟的端）。同时识别时第一张固定跟 Steam 端、第二张固定跟 TapTap 端；不是同时识别时只有第一张，按设置找窗口。`LaneHotkey` 是给一张的跟随部件用的热键登记口：每张只算自己要不要登记，由 `Lanes.set_hotkey_enabled` 合并成「任一张要登记就登记」交给唯一的热键线程。启动时设置就是同时识别时，`overlay_parts/app.py` 的 `main()` 用 `Lanes.wire_primary()` 接第一张、`add_secondary()` 一并建第二张；运行中改设置走 `Overlay.set_platform` → `Lanes.set_platform`：改成同时识别就加第二张，改回别的就 `remove_secondary()` 收掉（停识别线程、存它那四项、关它的识别记录、删窗口）。第一张不重建、对局状态不清，只换跟的端（`Watcher.set_platform`）。收掉第二张以后原来的端设置恢复，第一张按设置找窗口。
- 端标签：`Lanes.update_lane_tags` 在 `add_secondary`、`remove_secondary` 末尾按现在有没有第二张设两张的标签：同时识别时第一张写 `capture.PLATFORM_TAGS[STEAM]`、第二张写 `capture.PLATFORM_TAGS[TAPTAP]`，悬停说明是 `LANE_TAG_TIP`；只有一张时第一张设成空。`Overlay.set_lane_tag` 设字、悬停说明、显示或藏起，再刷新。`overlay_parts/layout.py` 的 `build_head` 建的 `lane_tag` 在标题栏这一行的最前面（`head_lead` 之前），只选一个端时藏着、不占地方。摘要能用的宽度（`_summary_width`）把标签的宽和一个间距算进去，放不下时照原来的办法先缩短、再从末尾省略；标题在正中的皮肤（`OverlayLook.TITLE_CENTER`）的 `head_lead` 宽要减去标签的宽和一个间距，标题才仍在正中；`HEAD_ALIGN` 为 `bottom` 的皮肤里它和右边的按钮一样靠下。样式表里有一条通用的 `QLabel#laneTag`（`theme/sheets.py`），各套皮肤在自己的 `SHEET_EXTRA` 里另改，按面板底色配字色和框线：它是直接写在面板上的，不在卡片上；浅色卡片的皮肤面板是深色，别照卡片里的胶囊配色。标签不能把标题栏撑高。`set_lane_tag` 的刷新要等 Session 的锁，锁正被占着（识别线程在算）时不在这里等，这一轮事件处理完再刷新：`remove_secondary` 存第二张的设置只等有限的时间（`EXIT_SAVE_WAIT_S`），不能又卡在这一步。
- 找不到游戏窗口的那张的层次：`window_plan` 的 `companion` 是另一张的前台状态（`Overlay._companion_activity`：两张都在界面线程，直接读另一张的 `WindowFollower.activity`；只有一张时为 None）。只有 `state == "nogame"` 时看它：另一张是 `game`、`own` 时这张也置顶，玩家才看得见「未找到」的提示；另一张的游戏切到后台（`background`）、最小化（`minimized`）、也找不到游戏窗口或者没有另一张时照旧不置顶（不浮在别的程序上面，另一张的游戏是玩家自己收起来的也不跟）。识别照旧暂停、热键照旧不登记、胶囊和悬停说明不变。从 `top` 退回 `none` 时，Win32 的 `HWND_NOTOPMOST` 会把窗口放到普通窗口的最上面，刚切到的程序在它下面、被它盖着：所以原来是置顶、现在因为找不到游戏窗口退回不置顶、另一张的游戏又切到后台或最小化时，`WindowFollower.apply_layer` 再调 `winapi.step_behind_foreground`，把窗口放到前台窗口的正下方（前台是拾星助手自己、置顶窗口、桌面或者没有前台窗口时不动；从托盘「显示」回来是从 `front` 算起的，玩家正要看它，不退到后面去）。不用另加计时器：找不到游戏窗口时 `update_activity` 每 `POLL_MS`（0.3 秒）照样走到 `update_plan`。
- 玩一个游戏时另一张的层次和两张的先后：`window_plan` 里 `companion` 除了 `nogame`，还在 `state == "background"`、`companion` 是 `game`、`own` 时起作用：这一张照样置顶（三选一显示着时 `front`，否则 `top`），不看 `covered`；截取屏幕时照旧暂停（`screen-background`），但也置顶。玩家正看着另一个游戏，两张悬浮窗都在游戏画面范围里，退到那个游戏的窗口后面就整个看不见了。查「被盖住」时另一个游戏的窗口不算：`winapi.probe_game` 的 `ignore` 从 `covering` 找出来的窗口里去掉它，再取最下面的那个；`Lanes._other_game` 给出另一张的 `follower.game_hwnd`（另一张找不到游戏窗口时为 None：那时 `game_hwnd` 还留着上一次的）。两张都置顶（`top` / `front`）时，`Lanes.restack` 把 `activity == "game"` 的那张排到另一张上面：`winapi.below` 看它已经排在下面就不动，否则 `winapi.bring_to_front`，识别记录记一条 `layer_order`（`top` 是哪一端）。`bring_to_front` 会让这一张越过开着的独立窗口（设置、编辑方案等，`WindowStack` 只有第一张那一份）：两张都是 `top` 时再照打开的先后把它们 `bring_to_front` 回悬浮窗上面、`mark_layer` 记成 `top`（同 `Tray.show_from_tray`，和只有一张时一样压在悬浮窗上面；只调 `relayer` 不够，它们记着的层次已经是 `top`，不会再设一次）；另一张在三选一（`front`）时不放回，那时悬浮窗本来就盖过它们。`restack` 在 `WindowFollower.apply_layer` 层次变了的那一次、`update_activity` 前台状态变了的那一次调用，不每次刷新都调（排一次先后要往下数顶层窗口）。另一个游戏出三选一、它的那张跳到最前面提醒以后，同一次 `apply_layer` 末尾的 `restack` 随即让前台那张排到它上面。
- 两张的摆放：第二张没拖动过（`rel_custom` 为假）时避开第一张。`WindowFollower.target_position` 把 `companion_rect`（另一张显示着时的 `frameGeometry`）交给 `live_placement` / `overlay_position` 的 `avoid`：三选一时按 `AVOID_WEIGHT`（2，挡住另一张整个看不见，比挡住「刷新」按钮的 3 轻）算进挡住的代价；不是三选一时算出的位置和它相交就换成 `geometry.beside`（依次试左边、右边、下边、上边，取第一个整个落在屏幕的可用区域里、又不和它相交的；先试左边是因为默认位置在游戏画面右边缘）。`place`（建出来时，没有游戏窗口的那一支也挪）、`poll`（每次查看游戏窗口：另一张被拖走、自动让开、变高变矮时）让第二张跟着挪开，它自己变高变矮时照旧由 `fit_height` 经 `reposition` 重算。谁让谁看 `companion_fixed` 和 `yields`（`Overlay` 传 `yields=lambda: self.primary is not None`）：第二张一直让着第一张；第一张只在第二张拖动过（位置固定）时避开它，没拖动过的第二张会自己让开，免得两张来回躲。`lane_settings.LaneSettings` 的 `window_rel` 只认 `lanes[端]` 里的（没有时为 None，按没拖动过算），不再照抄第一张的：照抄会被当成拖动过，两个游戏摆在同一处时第二张不会让开；`window_pos` 等其余三项照旧没有时用共用那份顶层的值，`_clean_lanes` 认 `window_rel` 为 null。
- 只有一份的部件：`Overlay(..., primary=第一张)` 建第二张，`_attach_primary` 把 `dialogs`、`windows`（独立窗口的层次）、`updates`（检查更新）、`previews`（皮肤预览图）、`relaunch_ack` 换成第一张的。这一步在第二张的 `WindowFollower`、`Tray` 建好以后才做，所以建它们时传的独立窗口那几样回调（`relayer`、`open_windows`、`mark_layer`）写成用到时再取 `self.windows`（`lambda: self.windows.relayer()` 这样），不直接传 `self.windows.relayer`：直接传就一直接着第二张自己那份空的 `WindowStack`，第二张从托盘「显示」时只把自己排到最前，不把独立窗口放回它上面，层次变了也不重设它们。`cancel_settle` 例外，第二张的是空操作：关掉在前台的独立窗口时临时置顶的那一轮（`before_window_hides`、`settle_tick`、`drop_lift`）只在第一张不置顶时开始，只管第一张和独立窗口；第二张的层次变了不打断它，打断了，临时置顶的就不再退回，一直留在置顶上。共用的 `WindowStack` 的 `window_id`、`layer` 回调是第一张的：第二张调 `relayer` 只是照第一张的层次再设一遍（记着的层次对得上时不调 Win32），不会两张来回抢着设。所以独立窗口的层次只跟第一张：第一张不置顶、第二张置顶时（例如 Steam 没开，TapTap 的游戏在后台、直接截取照常置顶），独立窗口在第二张下面。第二张的「设置」「导入/导出」「编辑方案」三个按钮先断开第二张自己那份 `Dialogs`，再接到第一张的；「编辑方案」单独接 `_open_editor_lane`，用 `Dialogs.open_editor(hero=第二张当前的角色)`，从第二张打开时编辑窗口停在第二张的角色。第二张的提示行 `NoticeModel(lane_only=True)` 只留本局提示和「识别已停止」，更新、下载、程序文件夹、热键、免费声明这些全局提示只在第一张显示。为什么这么做：托盘、更新、设置和各窗口全程序只有一份状态，第二张再建一份会让两边的窗口层次、下载进度、设置值互相对不上。
- 设置和热键状态的同步：第二张的 `set_manual`、`set_lowend`、`set_opaque`、`set_skin`、`set_platform` 开头就转给第一张（`if self.primary is not None: self.primary.set_xxx(...)`），第一张改完回调 `Lanes.sync_from_primary()`：把窗口上的副本、识别线程换掉，`LaneSettings.sync_from_shared()` 抄共用设置，第二张正显示着等待提示时按新模式重写（例如自动模式切到手动模式，要写该按哪个键）。热键文字、能不能用、不能用的原因用 `sync_hotkey_state()` 抄过去。不经过第二张自己的 `set_xxx`：第二张存盘只写自己那四项，会悄悄丢掉 `skin`、`platform_seen` 这类共用项，而且转过去又会转回来。
- 方案同步：`SchemeStore` 全程序一份（哪个角色用哪套方案）。任一张换了方案（方案下拉框、编辑窗口新建复制、导入后点「使用这套方案」）都走 `_use_scheme`，存好以后调 `Lanes.scheme_changed(self, hero)`：只叫另一张、不来回转；给了角色时和另一张当前角色不同就不动（各角色用的方案互不影响），相同才让另一张 `_schemes_changed(hero, notify=False)` 按自己的角色、地图、三选一重算；另一张这一局按地图换着方案时不动它。编辑窗口新建复制、导入后「使用这套方案」用 `lanes.lane_for_hero(hero)` 找哪一张当前角色是它：哪一张是就哪一张当场换用；两张都是时第一张换用、第二张跟着重算；都不是时只记下。
- 热键的先后：`Lanes.on_hotkey` 先选跟随部件的 `activity == "game"`（游戏窗口在前台）的那一张，先叫它识别；另一张等这一张的 `capture_done`，或者满 `PENDING_WAIT_S`（5 秒，在界面线程里用 `QTimer` 计时）再叫。先叫的那一张没开始识别（热键控制器不正忙）时直接叫另一张。几种不叫另一张的情形：另一张的识别已停止（`notice_model.recog_stopped`）、识别图片正在下载挡着识别（`_assets_blocked()`）、截取屏幕方式且它的游戏窗口不在前台（这时在它的悬浮窗上写一句 `SCREEN_BEHIND`）、第一张正在换热键（只在第一张上换）。直接截取游戏窗口时，被盖住的那一张照样识别。
- 下载识别图片挡着时两张一起暂停：`Background.also_pause` 在第一张上返回第二张的识别线程，`_set_blocked` 和下载完的 `reload` 对两张都做；第二张判断「下载挡着」看第一张的 `_assets_blocked()`（下载只有第一张做）。
- 关闭和退出：第二张的 × 只藏这一张（悬停说明 `LANE_CLOSE_TIP`），没有系统托盘时也一样；第一张有托盘时收到托盘，没有托盘时退出程序。托盘菜单的「显示」（`Tray.show_more`）和再次启动拾星助手时，`Lanes.show_secondary` 把第二张一起显示：第二张的 `Tray.show_from_tray` 也把开着的独立窗口照打开的先后放回它上面，和第一张一样。托盘菜单的「重置悬浮窗」（`Overlay.reset_overlay`）两张一起做：先做第二张再做第一张（第一张的 `show_from_tray` 会把第二张也显示出来，先做第二张它的 `hidden` 才是点之前的真实状态），两张都全部展开、清掉收起记录并显示；`_center_after_reset` 把第一张放到主显示器正中，第二张用 `geometry.pair_position` 紧挨在它右边（右边放不下时依次试左边、下边、上边，主显示器放不下时到别的屏幕找，都不行时叠着放），两张都当作用户拖到了那里；两张各记一条 reset 识别记录，最后 `Lanes.restack` 把游戏窗口在前台的那张排到上面。在第二张上调用会转给第一张。退出时 `Lanes.shutdown` 先取消性能测试并等它最多 2 秒，再叫停文字识别线程数的自检（`OcrCheck.shutdown`）并等它最多 2 秒，这两样都要看识别线程的状态；再对两张的识别线程同时发 `request_stop`，各做 `window.shutdown(shared=..., stop_watcher=False)`（第二张先收），最后两张共用一个 `SHUTDOWN_WATCHER_S` 的期限分别等 `watcher.stop(剩余时间)`；没停下的各记一条错误记录（第二张另写「第二张悬浮窗的识别线程当时停在」）。`save_secondary` 在 `EXIT_SAVE_WAIT_S` 内拿锁存第二张，拿不到记错误记录、这次不存；第一张仍由 `_save_on_exit` 存、把交给后台的写盘写完；最后 `close_recorders` 关两份识别记录。
- 性能测试：`Overlay.start_dual_test` 单独起一个守护线程（名字 `dual-check`）跑 `DualCheck`，每次测试一个序号。开测时两张的识别线程都 `set_paused("dual", True, why="dual")`，测完、取消、出错都恢复；取消以后迟到的结果只清理，不恢复、不回调（免得取消后马上重测时，旧线程的结束把新一次的暂停解开）。暂停、恢复都在界面线程做。

- 文字识别线程数的自检：`vision/ocr_check.py` 量、`ui/overlay_parts/ocr_check.py` 的 `OcrCheck` 决定什么时候量、量完存哪、提示栏上写什么。为什么：线程数合不合适和电脑有关，大小核的电脑上 4 个线程可能落在小核上、还要和游戏抢核，一次识别由最慢的那个线程决定。做法：用程序自己画的 1568×736、十来行字母数字的图（和一次三选一送去识别的那一块差不多大），按 `CANDIDATES`（2、4、8）各建一个引擎（自检另建的，不碰全进程共用的那一个），各读一次热身，再轮流量 `ROUNDS`（5）轮、每轮换一个先后，取中位数；读字时拿 `_ENGINE_LOCK`（和真正的识别不重叠），拿到锁才开始计时，每读一次歇 `REST_S`。挑法 `pick`：先取最快的，再从少的线程数往上看，第一个不超过「最快 × `CLOSE_ENOUGH`（1.15）」的就是结果，少占核心给游戏多留。什么时候量：启动 30 秒以后开始看（`FIRST_DELAY_MS`，之后每 `POLL_MS` 看一次），游戏窗口在前台、两张都不在对局里（中途退出一局的见「中途退出一局」那一条）、识别没暂停（没在下载那一大批挡着识别的图片、没跑性能测试；只补少量图片、被拒绝过以后慢速下载时识别照常，也可能量）、低配模式关着时才量；叫停、暂停、低配模式开了、哪一张进了对局就停（`_should_stop`）。量不出来时（叫停、同一个线程数忽快忽慢差 `NOISY_RATIO` 倍、`BUDGET_S` 内不够 `MIN_ROUNDS` 整轮、出错）一律照 `chip_select.OCR_THREADS` 的默认值；累计最多试 `MAX_TRIES` 次（跨启动，核心数变了从 0 算），这次运行最多开始 `MAX_RUNS` 次。提示栏（标题栏下方，`notices.ocr_check_row` 排成提示行，文字是 `wording.py` 的 `OCR_CHECK_*`）：量的时候一条绿字（级别 `ok`，样式表 `#notice_ok`，用每套皮肤的 `OK_COLOR`），写「正在进行性能自检，可正常进行游戏。」和剩余时间，`OcrCheck._tick` 每 `TICK_MS` 刷新一次。剩余时间是 `run` 的 `progress` 交的：活按份算，读一次连同歇一下一份，建引擎加热身抵 `WARMUP_SHARES` 份，按到现在为止每份花的时间估后面的（`_estimate_left`，最多是 `BUDGET_S` 的余量加一轮）；还没量到东西时按 `first_guess`；显示的数只往下走，估的多出 `JITTER_S` 秒以上才往上改。量完换成「自检结果：……」：量出来的按用上的线程数读一次的中位毫秒分三档（不超过 `FAIR_MS` 良好，绿字；不超过 `POOR_MS` 一般，说明色；更慢较差，⚠ 橙色），`BUDGET_S` 内量不完的写「性能很差」（⚠ 橙色）；忽快忽慢、出错只写这次没测出来、没能测完（说明色），次数没用满时写下次启动再测；较差、很差、忽快忽慢时后面接查到的原因，一般、查到排在小核上时也接（下一条）。较差、很差的留到玩家点「关闭本条提示」或回答「是」「否」（`KEEP_KINDS`，对局进行中先不显示），查到原因的忽快忽慢、一般也留着，其余 `RESULT_MS` 后自己收起；中途停下（叫停、进了对局等）只去掉提示，之后再量；两开时只在第一张上显示。这一条不存盘，下次启动不再显示。结果存在 `state.json` 的 `UiSettings.ocr_check`（量出来是 `cores`、`threads`、`ms`、`rounds`，没量出来是 `cores`、`tries`、`why`、`ms`），诊断包的 `settings.json` 里看得到；有效记录（核心数相同、线程数在候选里）只在启动时 `use_ocr_threads` 用上，不再量（记着 `retest` 又没用满次数的除外，见下一条）。它和低配模式：低配模式开着时照旧用 `LOWEND_OCR_THREADS`（2），量出来的结果等低配模式关掉才生效。打包自检里「识别合成图」一项用同一张图（`diagnostics.ocr_render_check`），保证发行版里画得出、读得出。
- 自检结果差时查原因（结果一般时在有大小核的电脑上只比只用大核）：`vision/ocr_reason.py` 查，`OcrCheck._work` 调用它，句子在 `wording.py` 的 `OCR_REASON_*`、`ocr_reason_text`。为什么：玩家看到「性能较差」时想知道是哪一件事、能不能改，列一串可能的原因帮不上忙；结果一般时读一次不算慢，别的原因不值得提，但大小核的电脑上文字识别被排到小核时，只用大核往往还能快不少，所以只看这一件。做法：开始量的时候 `begin` 建一个 `Probe`，记整机、本进程、游戏进程（各张悬浮窗对应的进程号，只用 `PROCESS_QUERY_LIMITED_INFORMATION` 打开、只读处理器时间）用掉的处理器时间，和 PDH 的处理器性能、限速；结果差时 `find` 收尾，再读电源、内存、本进程的省电设置、优先级、能用哪些核、处理器有没有 AVX2（`read_state`）。有大小核时另外比一次只用大核的收益（`ocr_check.big_core_gain`：不限制和只用大核轮流读，过了 `GAIN_BUDGET_S` 秒、又读够两轮就收尾，比完放开限制，再按设置放回；本进程被设成省电或被限核时比出来的不是核的大小，忽快忽慢时比出来的可能只是抖动，设置里已经开着或玩家说过不要时用不着，都不比）。`diagnose` 按表列出成立的原因，只看读到的数，读不到的一律当没查到；`shown` 挑最多两条：一条只能玩家自己做的，一条能替玩家改的（放最后，只问这一件）；较差、很差一条都没查到时写「可能的原因」，问要不要打开低配模式。结果一般、这台电脑有大小核（`sysinfo.has_big_cores`）时也调 `find`，带 `cores_only`：什么时候比照上面，要写的原因只留「排到了小核」（`small_core`），查到的别的原因不写，一条都没查到时不补「可能的原因」；比出来在小核上时和较差一样写原因、问「是」「否」、不自己收起（不记 `retest`），不到分界时只写「一般」那句、照常收起。比的时候提示栏照旧写剩余时间。比值不管到没到都存进 `readings` 的 `gain`，设置窗口「只用大核」一项的说明和出不出现按它（下一条）。能替玩家改的带「是」「否」（排在文字下面，一样宽：`STACKED_NOTICES`、`EQUAL_WIDTH_NOTICES`）：「是」（`OcrCheck.accept`）只改本进程自己的设置（省电声明、优先级、能用哪些核、`Overlay.set_big_cores`、低配模式），不碰别的进程和系统设置，改好了过 `RETEST_DELAY_MS` 再量一次，打开低配模式的不再量；「否」（`decline`）把这一项记进 `ocr_check.declined`，核心数不变就不再问。结果较差、原因是一时的（`TRANSIENT`，没插电、别的程序占着这类）时记 `retest`，下次启动再量，累计不超过 `MAX_TRIES`（和没量出来的那几次一起算）；再量没量出来时换回默认线程数，和提示上写的一样。读数（`readings`）和原因的键（`reasons`）存在设置的 `ocr_check` 里，诊断包看得到；分界线（`OTHERS_BUSY`、`ALL_BUSY`、`THROTTLED`、`LIMITED`、`LOW_MEMORY_GB`、`FEW_LOGICAL`、`GAIN_MIN`；`GAIN_MIN` 就是 `sysinfo.BIG_CORE_GAIN_MIN`，判定是 `sysinfo.on_small_cores`，设置窗口也按它）等诊断包里有慢电脑的读数以后再看要不要动。
- 只用大核（设置窗口的 `big_cores` 一项，存在 `UiSettings.big_cores`，标题写「允许拾星助手以高优先级运行以改善识别速度」）：`sysinfo.use_big_cores` 用 `SetProcessDefaultCpuSets` 设本进程默认用哪些核（效率等级最高的一级），对已经建好的识别引擎马上生效；任务管理器里优先级仍是「正常」。启动时 `main()` 按设置设上，`Overlay.set_big_cores` 改设置、设本进程（第二张转给第一张），设不上时不存「开着」、开关回到关。说明写两行（`settings/dialog.py` 的 `big_cores_desc`）：第一行写处理器名称（`sysinfo.cpu_label`：注册表里的名称去掉 (R)、(TM)、®、™，连续的空白并成一个；建窗口内容时读一次，读不到时写 `BIG_CORES_CPU_UNKNOWN`）；第二行在开关开着时写 `BIG_CORES_ON`（现在只在大核上），关着、这台电脑比出来在小核上时写 `BIG_CORES_SMALL`，其余写 `BIG_CORES_EFFECT`，`set_values` 时跟着换，拨了开关马上换。比出来的收益从设置的自检记录取（`overlay_parts/ocr_check.py` 的 `recorded_gain`：记录的核心数和这台电脑的相同时取 `readings` 的 `gain`，经 `Overlay.settings_values` 的 `big_core_gain` 交给设置窗口），到了 `sysinfo.BIG_CORE_GAIN_MIN` 才算在小核上（`sysinfo.on_small_cores`）；没比过、比出来不到分界时不说在小核上。再量时没比的（开关开着、结果良好、比到一半停下等），自检记录里留着这台电脑上一次比出来的 `gain`、另记 `gain_kept: true`（`OcrCheck._apply`；识别记录照记这次的读数，核心数不同的旧值不留），所以点了「是」、开着开关再量过以后关掉，照样写在小核上。出不出现（`big_cores_shown`、`shown_items`）：只在 `sysinfo.has_big_cores` 时有；开关开着一律有（要能关掉）；关着、比过、不到分界（本来就在大核上，只用大核没用）时没有。该不该有变了时，设置窗口关着就在 `set_values` 里按当前皮肤重建（`Dialogs.show_settings` 先更新再显示，下次打开就对了），开着时不重建，免得正在看、正在点的一行忽然没了。分界和判定放在 `sysinfo`（不碰 Qt），设置窗口不导入识别模块。说明在窄的窗口里不拆「大小核」「受影响」（`text.TIP_TERMS`）。固定高度的三套皮肤有这一行时窗口加高 `BIG_CORES_EXTRA`，按处理器名称很长、第二行写在小核上时「识别」页在各种截取状态下都放得下来定。
- 中途退出一局：回到主菜单时，认出主菜单就结束这一局（`session/offgame.py` 的 `SCREEN_RULES` 主菜单那一行，同房间要隔一会儿连续两次认出）。对局中读不到轮次时，看见轮次标记以后第一次读不到照认画面下方，第二次起离那次标记满 `pick_grace_ms` 才认（见「对局中先不判选角界面」那一条）：回到主菜单时第一眼多半就落在主菜单上，几秒内结束这一局；第一眼落在别的画面上（例如按 Esc 停在菜单上几秒再退出）时最多十来秒。认不出主菜单时（例如弹窗挡住了开始按钮和底下那排按钮），或者停在主菜单以外认不出的画面上时，这一局的状态（`Session.has_game_state`）一直留着，悬浮窗一直当这局还在打。所以 `vision/pipeline.py` 的 `FrameProcessor` 还记着连着多久看不到对局里的读数（`_count_quiet`）：读到轮次或看见轮次标记、三选一显示着或被隐藏着、读到玩家列表上的星数、「查看筹码」面板算对局读数（`_note_in_game`，从头算）；只算看着画面的时间，相邻两帧最多算 `QUIET_STEP_S`（暂停、手动模式不看画面、截不到画面的时间不算，刚从暂停恢复的第一帧不算），两开时给另一路让路的帧（`_yielding`）不算。满了 `[map_detect] quiet_ms`（1 分钟）置 `Session.game_quiet`（不存盘），又读到对局读数时清掉，两次各记一条识别记录 `read:quiet`。它只管两处：悬浮窗上对局中先不显示的提示（`Overlay._playing`：换繁体界面、软件内更新、性能自检的结果，经 `SessionView.game_quiet`），和性能自检能不能开始、要不要停（`OcrCheck._in_game`）。这一局记的状态、结束一局和开新的一局的判断都不动；软件内更新下好以后的自动重启也不认它（`Overlay._unfinished`，见「软件内更新」的「换上」）：对局中按 Esc 停在菜单上、战斗很长时这一局并没有结束，重启会丢掉这一局记的状态。时限为什么是 1 分钟：识别记录里战斗等画面最长近 50 秒读不到轮次（算上星数近 40 秒），比 `after_game_ms`（30 秒）长；误判的代价是对局里这几条提示跳出来一下、自检开始后又停下，按不在对局里晚一些的代价只是提示晚一点出来。停在主菜单时（认出主菜单、交给记账以后不在对局里了：还没有对局状态，或本局已结束）`FrameProcessor` 不做文字识别（主菜单空转，`_note_menu`、`_menu_idle`、`_menu_leave`）：只看底栏那一条和开始按钮那一块（`MENU_REGIONS`）的指纹，和认出时一样、画面尺寸也一样，这一帧就一项读数都不排，「查看筹码」面板、任务栏也不看；主菜单的背景动画、左下角轮播的横幅不在这两块里，变了照样空转。这两块变了、画面尺寸变了、按热键、从暂停恢复、界面上改了对局状态时不再空转：先看一眼下方区域，下一帧整幅识别（选角界面有时只显示一两秒，「匹配成功」画面三四秒），再照常读；三选一显示着时也不再空转（在对局里了，不看这一眼）；空转满 `MENU_IDLE_MS`（1 分钟）照常认一次，还是主菜单就接着空转。两块里有一块自己会变（开始按钮附近有动画等）时，空转会刚开始就停、看一眼又认回主菜单，来回进出比不空转认的字还多，所以记来回（`_menu_trip`）：因为这两块变了不再空转、之后没认出别的画面、`MENU_TRIP_MS`（10 秒）以内又重新空转算一次；`MENU_FLAP_MS`（1 分钟）以内满 `MENU_FLAPS`（3）次时，每次都只是开始按钮那一块变了的，这次停在主菜单期间（认出别的画面、窗口大小变了、从暂停恢复为止，`_menu_stay_over`）只看底栏；底栏也变过的，1 分钟内不空转、照不空转时读，过了再试，最坏和不空转时一样。单靠底栏分得开：底栏在主菜单之间只差 0～0.0023，和离开主菜单以后的画面至少差 0.17，开始匹配、进房间都是整屏换画面。识别记录 `read:menu_idle` 判的时候各记一条（`why` 为 `bar_only`、`flapping`），判过以后来回的那几次进出不记。本局还没结束时认出的主菜单不空转，结束一局照旧要两次认出；空转的帧照常算进连着多久看不到对局读数。为什么这样做：主菜单的背景一直在动，「画面没变就不认」挡不住，不空转的话停在主菜单时每分钟要认几十次字（读轮次、看下方区域、整幅识别）。
- 对局中少找字（`vision/pipeline.py` 的 `FrameProcessor`）：对局中的文字识别大头是「结果一轮才变一次、却每次都重新找字」的几样，找字占一次读数的六到九成。下面三样都不改读出来的数，只是少找字、少认字：
  - 三选一快读（`_select_read`，开关 `[watch] select_fast`，默认开，低配模式不动它）：完整读（`chip_select.read_chip_select`）认出三选一、位置记得下来（`chip_select.select_layout`）时记一份位置（`_select_layout`，只留最新的一份；两个客户端各有自己的识别流程，各记各的）。之后要认三张卡、画面大小和记下时相同时先快读（`chip_select.read_chip_select_fast`：只裁几小块认字、不找字），读成了就用它；退回（交回原因）、没记着位置、开关关着时照旧完整读，完整读认出三选一就重记位置（记不下来时留着原来那一份：动画那几帧完整读也读不全）。按热键的那一帧、补认（`_reread_at` 到点）那一次走完整读：前者是手动核对，后者本来就是再要一个意见。快读读成时等同认出了简体或繁体的标题（`Session.on_language` 传 False）。动画那几帧不另外等：退回就当场完整读，最坏和原来一样慢。识别记录 `read:select` 另有 `how`（`fast`）、`fast_miss`（退回原因），耗时记成 `read:select_fast`。快读的认字（`_recognize_crops`）也在引擎锁里排队。
  - 读轮次先只认字（`_round_quick`）：完整读读到了轮次、也看见了标记、交回了标记左边那一块（`hud.Hud.round_crop`）时记下（`_round_memo`，连同画面尺寸）。之后读轮次（不按热键、不连带读上方整块）先在那一块只认字（`hud.read_round_crop`），认出记账手上的轮次或往前一轮（`ROUND_STEP`，同 `_peek_round`）才当作读到了、照完整读读到时一样往下走；认出别的数、认不出、画面尺寸变了照旧完整读，别的数不直接交（理由同 `_peek_round`：画面没变时连读两次很容易满足，读错的数会绕过核对）。三选一上读左上角也一样。离开对局（`_left_game`）时清掉；换了界面语言（标记宽度不同）那一块对不上，自然退回完整读、重记。只认字看不见标记：离最近一次完整读看见标记（`_full_mark_at`，读没读到数字都算）满 `after_game_s`（`[map_detect] after_game_ms`）时这一次不先只认字、直接完整读，完整读看见了标记从那时重新算，没看见就之后每次都完整读，直到再看见标记。不这样的话，对局外的画面万一在那一块上正好认出手上的轮次或往前一轮，就一直当作读到了轮次，认选角界面、对局外的画面、离开对局后的整幅识别（都要读不到轮次才走）就一直不做；代价是对局里每 30 秒多一次完整读。识别记录 `read:hud` 另有 `how` 为 `crop`，耗时记成 `read:hud_crop`。
  - 进度条没变就不认字（`_read_progress` 给了 `now` 的那一路，即平时一轮读数里的那一项）：不在三选一时先看进度条的样子（`hud.progress_look`：只取进度条本体，即 `hud.progress_box` 里去掉上下和两头圆角外露着对局场景的地方（`PROGRESS_LOOK_TOP`、`PROGRESS_LOOK_BOTTOM`、`PROGRESS_LOOK_INSET`），缩成约 4×4 界面单位一个点的彩色小图，连同蓝色当前格（在整个 `progress_box` 里找）的位置；`progress_box` 和 `read_progress` 共用）。和上一次认字时（`_progress_seen`）一样（`hud.same_progress_look`，门槛怎么量的见 `hud.py` 的 `PROGRESS_LOOK_*` 注释：当前格挪一格、编号换了都算变了，录像压缩那种噪声、进度条背后的场景在动不算）、画面尺寸相同、离那次认字不到 `progress_s`（同 `unchanged_max_ms`，低配模式乘倍数）、那次读到了当前格、记账没有在等再读一次（`Session.progress_pending`）时，不认字，把那次的读数原样再交给 `Session.on_progress`（判新的一局时用的「最近一次读到进度」`_last_progress_read` 跟着更新）。只在已采用的数上沿用，不会凑成「连读两次」；红叉（进度上限）同理：那次读到了红叉、记账还没采用本局的进度上限（`Session.wants_progress_cap`，`_cap_wanted` 在锁里读）时不沿用，照常认字；看不到蓝色当前格时一律不沿用。三选一上照旧每次都认字（推荐要用这一刻的进度）。识别记录 `read:progress` 另有 `reused` 为 true。
- 对局中先不判选角界面（`vision/pipeline.py` 的 `FrameProcessor._pick_grace`，`[watch] pick_grace_ms`，默认 10 秒，低配模式乘倍数）：对局中（有对局状态、本局没结束）读不到轮次、轮次那一行的标记也没看见时，原来每次都紧接着认一次画面下方（`_read_pick`：选角界面和对局外的画面），这一项约占对局中文字识别的三分之一，可那时几乎都还在对局里（战斗一挡十几秒）。现在看见一次标记（`_mark_seen_at`，完整读看见的、只认字认出的都算）以后，第一次读不到照判（`_grace_mark` 记下照判过的是哪一次标记）；第二次起离那次标记不到 `pick_grace_s` 时，这一轮的 `pick` 换成 `stars`（和判了「不是」以后一样读星数），并 `perfstats.count("pick_grace")` 记一次（识别记录 `recog_stats` 的 `counts`）。第一次照判为什么要有：打完一局时结算画面紧跟在棋盘之后出来（实机记录里最后一次读到轮次以后 3.6～4.0 秒认出），有时不到 9 秒就过去了，结算画面一般就是这一眼认出的；中途退回主菜单、房间时这一眼也多半落在上面，认得和原来一样快。另外照判的几种：按热键（`force`；按热键的那一次不算「第一次」，之后第一次自动读不到还照判一次）；刚从暂停恢复、还没读到轮次（`_stale`：暂停期间可能早就离开了对局）；看颜色认出打完时的斜带或通关的红底以后 `pick_grace_s` 以内（`_check_victory` 在 `victory.RUN_S` 以内的那几帧把 `_ending_seen_at` 记成这一帧的时刻；只管这么久，不管这一局剩下的时间：对局中途偶尔也有颜色像的画面，记成「这一局都照判」的话，像过一次以后这一局就再也不先不判），第一眼落在斜带、红底或过场上、结算画面后面几眼才出来时靠它（看见标记以后第一次读不到照旧照判、记下 `_grace_mark`，这一条管之后的几次）；离上次看见隔了 `pick_grace_s` 以上时记一条识别记录 `read:finish_look`（`look`、`coral`、`white`），事后对得上是哪一幅画面（`pick_grace_s` 为 0 时不记，不然颜色像的每一帧都记一条）；同一次也把这一帧留成待转正的一张（`_note_finish_look`：缩到长边 1280，连同当时的 `look`、`coral`、`white`、轮次和原图尺寸）：之后这一局又读到轮次标记、离留下满 `pick_grace_s` 时转成 `finish_shot`（说明这一局接着打下去了，是对局中途的画面像打完），导出诊断时另存 `finish-look-<时分秒>.png`；本局结束、离开对局、留下以后判了新的一局（`WatchHints.games` 变了：游戏切到后台期间打完一局又开了一局，回来时可能不经过选角界面、对局外的画面，直接读到新一局变小的轮次）时丢掉待转正的那一张，读到变小的轮次、记账还在等再读一次（`round_drop_pending`）时先不转正。`finish_shot` 只在内存里留最近一张，本局结束不清（玩家多在打完以后才导出）；`pick_grace_ms` 为 0。代价：第一眼落在别的画面上（例如按 Esc 停在菜单上几秒再退出）时，中途退回主菜单、房间最多晚 10 秒认出；这时退回去马上又开一局、10 秒以内就到了选角界面可能漏看。时限按一局实机记录定：对局中读不到轮次、判了选角界面的 26 次里，第一次照判、之后时限取 10 秒能先不判 9 次（约三分之一），15 秒 11 次，20 秒 14 次，6 秒一次也省不掉；取 10 秒，再长省得不多，第一眼没落在主菜单、房间上时又认得更晚。
- 文字识别引擎的锁：`vision/chip_select.py` 的 `_ENGINE_LOCK`。引擎只有一个实例，`recognize_only` 调用时还会改引擎上的开关（`use_det` 等，改完必须还原），两个客户端同时识别时两路各读各的画面，不能同时用。用引擎的地方（`recognize_only`、`_ocr_lines`、`_reread_count`、三选一快读的 `_recognize_crops`，以及每帧读字走的 `io.ocr`）和换线程数的 `use_lowend_threads` 都在这把锁里排队，一次只有一个线程在用，另一路等它读完。`io.ocr` 给了 `det_side`、`pad=False`（读进度条，见 `anchors.PROGRESS_DET_SIDE`；判选角界面那一次也给了 `det_side`，见 `anchors.SELECT_DET_SIDE`：画面下方那一块字够大，短边只放大到 320，不补边那一项不用动）时，也是在锁里临时改引擎找字一步的设置（`text_det.limit_side_len`、`width_height_ratio`），识别完、出错时都马上还原，别的识别和另一路照旧按引擎的设置。锁里只包用引擎的那一下：裁图、缩放、按文字找位置都在锁外，两路的大部分时间照常并行；锁里不做耗时的事，否则另一路会白等。低配模式只有一份设置，两路排着各换一次，换完结果相同；开关是全进程的，识别线程每帧按 `lowend_threads()` 看得出来，别处换过时下一帧照自己的低配模式再换回来。
- 一路的三选一显示着时另一路让路：引擎排队时，三选一那一路的每一次文字识别（认三张卡、先读完的轮次和进度条、核对）都可能要等另一路正在做的那一次，推荐跟着晚出来。所以两路共用一块牌子 `vision/pipeline.py` 的 `SelectBoard`（`Lanes.select_board` 建一份，经 `Watcher.select_board` 在识别流程建好时交给 `FrameProcessor.board`）：每一路每帧认完三选一以后在上面记一笔（显示着、推荐还没给时记下时刻；推荐给过了、没显示、被隐藏着、`watch_idle`、识别流程重建或线程结束时擦掉。推荐给过以后那一路只盯绿框，基本不用引擎，玩家一直不选时另一路的读数不该跟着变旧）；另一路记着的时候，自己不在三选一时平时的读数里要做文字识别的几项（`OCR_STEPS`：读轮次和轮次被挡住时的那一眼、认选角界面、读队友、存立绘模板、读进度条、离开对局后的整幅识别，以及读星数那一项连带的读星币、按名字找自己）留到那边给出推荐或关掉以后接着做，这期间不设 `pending`；在对局里时照旧按 `hud_ms` 认角色、读星数（模板比对）；看自己有没有三选一（预筛、快速复查、需要时的完整识别）照旧，自己的三选一也显示着时各读各的。记号超过 `BOARD_STALE_S`（5 秒）没更新就不再算数：那一路卡在一次很慢的取帧里、停下了时自己不会一直让路。性能测试（`DualCheck`）的两路不接这块牌子：测的时候两个游戏都停在大厅，没有三选一。
- 模板缓存的锁：`vision/templates.py` 的 `VisionAssets.lock`（可重入锁，`reload` 里调 `reset_hints`，两者都要拿）。模板和沿用缓存只有一个实例（`templates.assets`），两个识别线程同时读写：一个线程重建缓存（`reload`，清空各张表）时另一个可能刚把一项存进表里、正要取出来，中间被清掉就抛 `KeyError`。所以 `stars.py` 的三张表（`_photos`、`_faces`、`_still`）的查和存，以及 `reload`、`reset_hints` 的清空，都在锁里做；读图片、缩放模板这些慢的步骤在锁外做，另一个线程读缓存不用等它。存进去以后返回自己建的那一份，不回头再取一次表里的，重建缓存在这两步之间发生也不会出错。
- 性能测试：`advisor/ui/dual_check.py` 的 `DualCheck` 在两个游戏窗口都开着时同时跑两路识别 30 秒，量三样——三选一出推荐最慢的一次、整机处理器被压满的时间占比、拾星助手自己占整机处理器多少，再按到了基准值的几成分五档。两条基准值（`SLOW_LINE_S`、`BUSY_LINE` 与 `BUSY_SHARE_LINE`）对着玩家关心的两件事：推荐来不及时、游戏卡不卡。每样数先算到了基准值的几成，取两样里大的那个（一次都没量到时只看处理器），按 `LEVEL_LINES` 分档：七成及以下余裕，超过七成到九成正常，超过九成到十成危险，超过十成到十一成临界，超过十一成过载。取大的那个，是因为一样已经让推荐来不及或游戏卡了，另一样再轻松也不该算轻松。对话框里余裕、正常直接开启（`DIRECT_OPEN`），危险默认「无视风险，继续开启」（`IGNORE_DEFAULT`），临界、过载默认「打开低配模式再测」（`RETEST_DEFAULT`）；结果标题只有档名那一段按档着色（`SETTINGS.LEVEL_COLOR`）。只看拾星助手自己占多少分不出这两件事，`own_share` 只写给玩家看。取帧节奏（`_pace`）有意比平时的大厅重：每取到一帧都按 `[watch] active_ms` 等，低配时 `active_ms` 也乘 `lowend_factor`，而悬浮窗的识别线程只在大厅按 `idle_ms`、低配时也不放慢 `active_ms`。测的时候两个游戏都停在大厅，大厅的帧比对局里的轻（读的东西少），取帧比大厅密，量出来的负担宁可偏重，不让玩家进了对局才发现吃不消。同样的道理，两路识别停在主菜单也照常认字（`FrameProcessor.menu_idle` 关掉）：悬浮窗的识别线程停在主菜单时不做文字识别（主菜单空转，见「中途退出一局」那一条），照它量的话几乎只剩取帧。测试只读画面、不写文件：对局状态不存盘，不记识别记录。低配时文字识别按低配模式的线程数测，测之前记下原来的样子，测完换回去。
- 已知局限：`advisor/perfstats.py` 的统计、`advisor/ui/screen.py` 的 `_last_state`、`advisor/vision/capture.py` 的 `_found` 是两路共用的，两路同时识别时混在一起，只影响诊断包和识别记录里的数，不影响识别和推荐结果。

## 已知局限

- Steam 版（国服「AstralParty_CN」、国际服「AstralParty_INT」）和 TapTap 版（「吉星派对」）可以同时运行。没有选「Steam端+TapTap端」时，自动识别一次只认一个游戏窗口：两个都开着时跟最后启动的那个（按进程启动时间），另一个不识别，要只认某一个客户端时在设置窗口的「游戏平台」里选定。选了「Steam端+TapTap端」以后两个客户端同时识别，每个客户端一张悬浮窗。第一张原来跟 TapTap 端时改成同时识别，它改跟 Steam 端，手上留着 TapTap 那一局的已有筹码、地图，不清（新的一局会重新认）。`advisor/vision/stars.py` 的 `_last_u`、面板的 `_last_fit`、`_last_skin` 各只存一份，两个游戏窗口大小不同时两个识别线程轮流覆盖，更占处理器（性能测试量到的数已经含了它）。`advisor/vision/hero.py` 的粗筛缓存按模板序号存，一个识别线程存了用户模板、另一个正在认角色时可能排得不准，很少见。设置文件以后总带着 `"lanes": {}`、`"ocr_check": {}`，基准工具（`tools/baseline/storage.py`）比对设置那一组时会有这两处差异，是预期的变化。

- 通关还是失败（只进推荐日志和对局报告，悬浮窗上不显示）：通关靠结算页之前约 2 秒的通关画面「VICTORY」（`advisor/vision/victory.py`：整屏珊瑚红底色，大字读得全的只有约 0.4 秒），打输靠棋盘上约 2 秒的皇家蓝斜带「GAME OVER」（同一个模块：蓝带占比和斜矩形的长、短边、斜度都对才算，再把画面转正认字，大字在带子左半边、会慢慢往左滑）。通关画面在繁体中文客户端、打输横幅在简体中文客户端的 3840×2160 录像上实测过，横幅是图片、简体和繁体客户端一样。奖励画面上「星币」那一格的数另作依据：通关按难度给 30～45，不少于 25 算通关；失败照游戏资料固定给 10，只有正好是 10 才算失败，画面上还没见过。只看到横幅算失败，星币是 0、10、读不到都一样（和电脑打的局不给星币，打输那段录像的奖励页上没有星币这一格）；横幅和星币数说法相反（星币 ≥ 25）、通关画面和横幅都看到时都算矛盾，两项都不知道。识别取帧太稀、游戏在后台时会漏看这两种画面，结算画面和奖励画面都没截到时这一局的胜负不知道；没看到横幅不算失败。房间等画面误认成结束以后、判出新的一局之前不看这两种画面。
- 流派加权倍率、刷新代价、剩余三选一次数、组合规则和队友调分的分值是按资料和经验估计的参数，待推荐日志积累后校准。
- 刷新后的最左格按「固定稀有度、仍按职业权重选职业筹码池，但池按筹码的职业标签建」计算（`[pool] reroll_leftmost = "class_tag"`）：带职业标签、不在池表里的筹码（磨刀石、电磁炮等）也可能出现。依据是实机 5 局 16 次刷新，样本少，攒到 30～40 次刷新后再核对。
- 刷新次数读不出时按「一次都没用过」补的默认值（可能的最多次数）计算，这时不按多出来的刷新算（之后还有三选一就只算刷新一次、按公式扣代价）；读到了时之后的三选一每次留 1 次、再多留 1 次以防「之后还有几次三选一」估少，多出来的才连着刷、不算代价。
- 队友姬梦朝的白泽赐福给目标施加【白泽祝福】（目标增加治疗溢出量的攻击力，持续 1 回合，状态到目标自己的行动结束才消失），目标自己回合开始时治愈溢出的那部分也在这段时间里，相关的队友调分按能转化计算；实际怎么结算在服务器上，未经实机核对。
- 识别画面的截取方式：Windows 10 版本 2004 起直接截取游戏窗口，游戏窗口不在前台、被其他窗口遮挡时都截得到，最小化时截不到（暂停识别）；Windows 10 上直接截取期间游戏窗口四周有黄色细框。游戏窗口不在前台或被完全盖住时，游戏本身可能停止绘制或降低帧率，这时识别到的是游戏最后画出的画面；游戏放在另一个虚拟桌面时可能一直截不到画面，约 20 秒后按出错改为截取屏幕。游戏是否会在后台停止绘制、开了 HDR 时颜色是否一致，都还没有在实机上核对。
- 截取屏幕（系统不支持直接截取、或直接截取出错时）：截的是屏幕上可见的游戏窗口，窗口不能最小化，被其他窗口遮挡的部分截不到，所以游戏和悬浮窗都不在前台时暂停识别。悬浮窗不会出现在识别用的画面里：识别时另行排除悬浮窗遮挡的区域补截，这几小块比整幅截图晚约 0.1 秒，悬浮窗压在正在变化的画面上时这一帧的两部分时刻不同，下一帧即改正。Windows 10 2004 之前的系统不支持让窗口不出现在截图里，系统改为让悬浮窗在截图里显示为黑块。
- 「盖住」只看窗口的位置、大小和样式：显卡、语音软件的全屏覆盖层大多是鼠标能穿透的，不算盖住；个别不透明、鼠标也不能穿透的覆盖层会被当作盖住，悬浮窗退到它后面。
- 同一时间只能运行一个拾星助手（开发版和发行的版本算同一个），再次启动时和点击托盘图标一样，把已在运行的悬浮窗显示出来，放到所有窗口的最前面（不激活）。以管理员身份运行的拾星助手在运行时，以普通权限再次启动的无法请它显示悬浮窗，也无法结束它：约 2 秒后弹窗说明，这时请点击托盘图标显示；它没有响应时，请在任务管理器中结束进程后重新打开。
- 手动模式下轮次一跳好几轮时，跳变来的轮次不算「确实到过」，新的一局多靠星数变少、角色变化或选角界面认出。
- 加载画面、「匹配成功」画面、房间设置上读到的地图和地图专属筹码对不上时，要专属筹码拿到手、或两次不同的三选一都指向同一张地图才改（任务栏认出的照旧一次就改）。
- 用系统自带的 tar 解压时，日文等区域设置下解不出「使用说明.html」这个文件名；请用资源管理器或其他解压程序。
- 下载识别图片、检查和下载更新都用系统自带的 WinHTTP（`advisor/winhttp.py`），和标准库的 urllib 有两处不同：从 https 跳到 http 的重定向不跟（防止被降级成明文），urllib 会跟；代理的用户名或密码含非 ASCII 字符时下载失败（WinHTTP 按系统代码页转换 Basic 认证）。PAC 和「自动检测设置」同 urllib 一样不认。
