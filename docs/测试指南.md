# 测试指南

这份指南写给帮助改进拾星助手代码的人。它按「先照着做、再用它查」来组织：新上手先看第一节；改了某处代码想知道该跑哪些测试，查第七节；某个测试跑出错，查第八节里那个测试文件对应的一节。

测试代码在 `tests/` 下，文件名都以 `test_` 开头；每个文件一节，按区域分章，一章一个文件，放在 `docs/test-guide/` 下（第八节有目录）。跑测试的工具是 `tools/run_tests.py`。指南里的路径都相对仓库根目录，用正斜杠。

## 一、三分钟上手

在仓库根目录运行（开发环境里用虚拟环境里的解释器，例如 `.venv\Scripts\python`；下面统一写 `python`）。三条最常用的命令：

```powershell
# 1) 跑全部快测（默认）：慢测试、实机测试以外的全部测试，按模块并行
python -B tools/run_tests.py
# 2) 只跑一个模块（短名，不加 tests.、不加 .py）
python -B tools/run_tests.py --only test_data
# 3) 跑慢测试（一个模块单跑就要一两分钟到几分钟的那几个）
python -B tools/run_tests.py --slow
```

各要多久（默认 8 路并行时的大约数，视电脑而定）：全部快测约 5 分钟，慢一些的电脑要十几分钟；慢测试约 4 分钟；快测加慢测试一起跑约 6 分钟；只跑一个模块看是哪个（第八节每节写了那个模块上一次大约跑几秒）。这些是估计，测试不等电脑空闲，别的任务占着 CPU 时会慢不少。

只跑一个模块也可以直接用 unittest：`python -B -m unittest tests.test_data`。

## 二、测试怎么跑

`tools/run_tests.py` 按模块并行跑测试。测试分三类，名单写在这个脚本开头：

- **快测**（默认）：`tests/test_*.py` 里除了下面两类的。
- **慢测试**（脚本里的 `SLOW` 名单）：`test_vision_matrix`、`test_resume_noise`、`test_session_fuzz`、`test_resume_frames`、`test_pipeline_sequences`、`test_real_games`。
- **实机测试**（脚本里的 `LIVE` 名单）：`test_window_capture_live`、`test_window_layer_live`，默认不跑，`--all` 也不含，要设环境变量才跑（见下）。

`tests/live_*.py`、`tests/private_data.py`、`tests/support/` 不是测试模块，不会被当成测试跑。

命令行参数：

| 参数 | 作用 |
|---|---|
| （不加） | 跑快测 |
| `--slow` | 只跑慢测试 |
| `--all` | 跑快测 + 慢测试（不含实机测试） |
| `--only a,b` | 只跑指定模块（短名，逗号分隔；写 `tests.test_data`、`tests/test_data.py` 也认） |
| `--jobs N` | 同时跑几个模块（默认 8） |
| `--timeout 秒` | 给每个模块定一个统一的限时秒数 |
| `--json 路径` | 另存一份机器可读的结果（JSON） |
| `--list` | 只列出要跑哪些模块，不跑 |
| `--no-excluded-imports` | 不查「程序用到了发行版排掉的模块」（默认查） |

跑法：每个模块单独一个子进程（`python -B -m unittest tests.<模块>`），工作目录是仓库根目录，环境变量继承；同一个模块里的用例仍是一条接一条串行，模块之间并行。并行路数由 `--jobs` 决定，另外「会真的建文字识别引擎」的模块（脚本里的 `OCR` 名单）同时最多 3 个，免得识别线程互相抢 CPU。

排序和限时：模块按 `.tmp/test-times.json` 里上次的耗时从长到短排（没有记录的按测试文件大小估），先跑长的。每个模块有超时上限，默认快测 1200 秒、慢测试和实机测试 3600 秒；上次耗时的若干倍更长时按倍数放宽。超时算失败，连同它起的整棵进程树一起结束。`--timeout` 给所有模块定一个统一的秒数。

界面测试不弹窗、不用开游戏：跑测试时会设 `QT_QPA_PLATFORM=offscreen`（已经设了的不覆盖），界面在离屏平台上画出来，不会在你的桌面上弹窗；识别测试用的是样本截图或构造的假数据，不用启动游戏，也不用显卡（少数几条要显卡的会跳过）。

实机测试要另外设环境变量，不设时整个跳过：

```powershell
$env:CHIP_ADVISOR_LIVE_CAPTURE = "1"
python -B tools/run_tests.py --only test_window_capture_live,test_window_layer_live
```

这两条会在所有屏幕范围以外开测试窗口和悬浮窗做真实截取、窗口层次，要用到显卡和几个核，打游戏时不要跑。

## 三、结果怎么看

跑完打一张汇总表，每个模块一行，最后一行是合计。每一列：

| 列 | 含义 |
|---|---|
| 模块 | `tests.<模块名>` |
| 结果 | 通过 / 失败 / 异常退出 / 没有用例 / 超时 / 中断 / 没跑（见下） |
| 条数 | 这个模块一共跑了几条用例 |
| 通过 | 通过的条数 |
| 失败 | 断言不成立（`failures`）的条数 |
| 错误 | 用例抛异常（`errors`）的条数 |
| 跳过 | 用例自己跳过的条数（`skipped`） |
| 用时 | 这个模块实际跑了多久（秒） |

「结果」这一列的几种状态：

- **通过**：这个模块最后一行结论是 `OK`（允许带 `skipped=…` 等），并且进程退出码是 0。
- **失败**：结论是 `FAILED (...)`，或有标了「预期失败」的用例反而通过了，或结论是 `OK` 但进程退出码不是 0（多半是用例跑完以后收尾时崩了），或整次运行里出现了下面「特别失败」里的任一种。
- **异常退出**：输出里没有 `Ran N tests` 这一行，或它后面没有结论行（进程中途没了）。
- **没有用例**：结论是 `NO TESTS RAN`，一条用例都没跑到。
- **超时**：超过限时还没跑完，已经连同它起的进程一起结束。
- **中断**：按了 Ctrl+C，正在跑的模块被结束。
- **没跑**：Ctrl+C 时还没开始的模块。

判定从严：只认输出里最后一个 `Ran N tests` 之后的第一行结论（用例自己打印的 `OK` 不算数），结论是 `OK` 还要退出码是 0。

整次运行的退出码：全部通过 0；有没通过的模块、或者程序用到了发行版排掉的模块 1；都通过了但 `--only` 里写了不存在的模块 2；按 Ctrl+C 中断 130。

几种特别的失败（会单独列在输出最后，汇总表这一行也标出来）：

- **测试动了用户的真实文件**（这一行标「！！」）：测试本应只写自己的沙箱，却碰到了你真实的设置、方案或日志。退出码 97，错误输出里有一行以「[沙箱] 测试动了用户真实的文件」开头（详见第四节的沙箱）。
- **悬浮窗分块刷新出错**（这一行标「！」）：测试进程默认的错误记录里出现了「刷新悬浮窗的「…」出错」。悬浮窗刷新时某一块出错只记进错误记录、其余几块照画，用例本身看不出来，所以要单独查。退出码 96。
- **程序用到了发行版排掉的模块**：程序（`advisor`、`rapidocr_lite`、`packaging`）的代码直接或经库导入了一个发行版用 Nuitka 排掉的模块（例如 numpy 的 `np.median` 会用到 `numpy.ma`）。这种在开发版和测试里看不出来，发行版里一调就报错，所以跑测试时单独盯着；有记录整次运行算没通过。导入它的库自己有退路、已登记的那几个不算失败，另起一行列出来。`--no-excluded-imports` 关掉它。

没通过的模块，它的输出会存到 `.tmp/test-logs/<模块>.log`，末尾附一行运行器的判断（判为哪种、退出码、说明），汇总表后面也会列出日志路径。这次通过了的模块，会把它上一次留下的日志删掉。`--json 路径` 把结果再存一份 JSON，字段有每个模块的状态、条数、耗时、有没有动真实文件、有没有分块刷新出错，整次有没有通过，以及「程序用到了发行版排掉的模块」的记录。

## 四、测试为什么不会碰你自己的设置和文件

测试进程启动时，`tests/support/sandbox.py` 会建一个沙箱，把测试会写的位置统统指到 `.tmp/test-run-<进程号>/` 下：环境变量 `APPDATA`、`LOCALAPPDATA`、`TEMP`、`TMP`、`TMPDIR` 都改指到沙箱里，`advisor/paths.py` 里决定设置、筹码方案、推荐日志、识别记录、诊断包、临时文件和错误记录位置的函数也换成沙箱版本。子进程也继承这些设置。沙箱在这个进程结束时删掉；上一步被强行结束、来不及删的，下一个进程会顺手清掉。

除了沙箱，进程开始时和结束时还会给一组你真实的文件（项目根目录的设置和方案文件、`logs`、`reports`、错误记录、`assets`，以及发行版个人目录）记一遍指纹，结束时比对。有变动、而且测试开始和结束时都没查到你在运行拾星助手（开发版或发行版）时，就报「测试动了用户的真实文件」，退出码改成 97（见第三节）。`assets` 不进沙箱——识别要读里面的图片——但程序运行时也会往这儿写（下载的识别图片、手动指定角色时存的立绘模板、皮肤缩略图），测试靠各自的替身把这些换走，沙箱是主要的防护，指纹只是事后核对。你正开着拾星助手时文件本来就会变，这时只打一行提示，不算测试失败。

所以正常情况下，跑测试不会改你本机的设置、筹码方案、日志、诊断包和下载的识别图片。

## 五、识别样本怎么准备

（本节就是跳过信息里说的「准备识别样本」一节。）

识别测试要读游戏截图和人工标注。这些样本不随仓库发布：体积大，而且截图上有玩家昵称。别人克隆下来的仓库里没有，跳过信息会写明缺哪个文件。自己截图、写标注就能跑。

**放哪里**：默认是仓库根目录的 `samples/`（截图和三份标注 `labels.json`、`stars_labels.json`、`panel_labels.json`），星币数的截图和标注在 `tests/data/coins/`（截图加一份 `labels.json`），认角色用的左下角裁图在 `tests/data/hero/`（不用标注：文件名、原画面大小和角色写在 `tests/test_stars.py` 里），「查看筹码」面板翻页、三选一被隐藏的录像帧、通关画面「VICTORY」和打输横幅「GAME OVER」的录像帧（含通关斜带那一行大字的裁图）、三选一预筛分数最靠近门槛的几帧（动画里的三选一、上下有黑边的窗口、开战转场）在 `samples/pages/`（不用标注，也不进三份标注：文件名和应读出的结果写在 `tests/test_panel_pages.py`、`tests/test_select_hidden.py`、`tests/test_victory.py`、`tests/test_prefilter.py` 里；打包自检和识别基准也读其中通关、打输的几帧，写在 `tools/build_release.py` 的 `VISION_SAMPLES`、`tools/baseline/vision.py` 的 `FINISH_FRAMES`），从卡面现裁角色照、推算裁法用的卡面原图在 `tests/data/cards/`（BWIKI 上的 `UT_Hero_Card_*.png` 原图，另在 `enwiki/` 里放英文 wiki 上同款的游戏角色照，用到哪几张写在 `tests/test_card_crop.py` 里）。截图文件名怎么起都行，标注里按文件名引用。几个目录都能用环境变量改（见下）。开发工具里的识别评测、截图回放、识别耗时等也读这些样本（只认仓库根目录的 `samples/`，不认下面的环境变量；`tools/eval_hud.py` 和推荐对比工具的识别领域另读 `samples/extra/` 下不写进标注的截图，见 `tools/eval_hud.py` 的 `EXTRA`），见软件维护说明「开发工具」。

**三份标注**（都是 UTF-8 的 JSON，顶层是 `{"_说明": "…", "samples": [ … ]}`，以「_」开头的键是说明，不读）：

- `samples/labels.json`：最主要的一份，一张截图一条。常用字段：`file`（截图文件名）、`size`（不是默认尺寸时才写，默认按 3840×2054，文件名里带 `_宽x高` 的也要和图片一致）、`scene`（这张是什么画面，如筹码三选一、任务栏、对局、结算页等）、`round`/`round_covered`（轮次、是否被挡住）、`map`（地图）、`tasks`（任务栏文字）、`progress`/`progress_cap`（进度条当前格和红叉格）、`offer`（三个候选筹码名）、`selected`/`selected_final`/`picked`（选中的、最终拿到的、绿框的）、`rarity`（候选筹码的稀有度）、`rerolls`（剩余刷新次数）、`probabilities`（三选一概率行的三个百分数）、`team`（这一行是不是全队三选一）、`hero`/`hero_covered`（角色、立绘是否被挡住）、`owned`（面板上的已有筹码）、`coins`/`price`（星币数、价钱）、`star`（星数）、`badge`/`badge_note`/`badge_unexplained`（游戏内置推荐角标）、`source`（三选一来源）、`screen`（对局外画面的读数，如结算页的地图、难度、轮数）、`note`（说明）。
- `samples/stars_labels.json`：玩家列表相关的一张截图一条。字段：`file`、`hero`、`own`（自己的星数）、`own_row`（自己是第几行）、`actual`、`rows`（每一行的星数）、`players`（各行的角色）、`bots`（哪几行是电脑）、`note`。
- `samples/panel_labels.json`：「查看筹码」面板相关的一张截图一条。字段：`file`、`is_panel`（是不是面板）、`hero`、`owned`（面板上的筹码）、`tab_count`（页签个数）、`selected_tab`（选中的页签）、`self_index`（自己在第几页签）、`selected_slot`（点选的格子）、`bottom_sprite`（底部像素小人）、`note`。
- `tests/data/coins/labels.json`：星币数截图一条。字段：`file`、`size`、`hero`、`own_row`、`own`（应读出的星币数，读不到为 `null`）、`rows`（每一行的星币数）、`why`（读不到的原因）、`how`（缺省按头像找，写「名字」表示头像认不出、按名字找）、`name`（本局记住的自己的名字）、`name_row`（按名字找到的行）、`note`。

标注里不写玩家昵称：截图上有昵称的地方在标注里不出现（核对时按代号）。

**`tests/data/private.json`**（也只在本机，不进版本库）：和真截图比对用的玩家名字，字段 `own_name`（样本截图上你自己的名字）。测试代码里不写这个名字。这个文件不在时，只有几条测试跳过，其余照常。

**五个环境变量**：

| 变量 | 作用 |
|---|---|
| `ACC_SAMPLES_DIR` | 改 `samples/` 的位置（截图和三份标注） |
| `ACC_COIN_SAMPLES_DIR` | 改 `tests/data/coins/` 的位置（星币数截图和标注） |
| `ACC_HERO_SAMPLES_DIR` | 改 `tests/data/hero/` 的位置（认角色用的左下角裁图） |
| `ACC_CARD_SAMPLES_DIR` | 改 `tests/data/cards/` 的位置（卡面原图和英文 wiki 上同款的游戏角色照） |
| `ACC_PRIVATE_DATA` | 改 `tests/data/private.json` 的位置（也可指到一个不存在的文件来试） |

五个变量的写法一样：设了就用它，否则用默认目录；设成空字符串也按没设处理（代码里写的是「取环境变量、空就退回默认」，见 `tests/support/samples.py`、`tests/private_data.py`）。值是路径，相对路径按运行测试时的工作目录算——`tools/run_tests.py` 把工作目录设成仓库根目录，所以就是相对仓库根目录；路径里有空格直接写，不用加引号（它是环境变量，不经过命令行拆分）。`ACC_PRIVATE_DATA` 也可以指到一个不存在的文件，用来试「本机数据不在」时的表现。

**没准备样本时会怎样**：需要样本的测试会跳过，不报错。跳过信息写明缺哪个文件，形如「没有识别样本：缺 samples\某文件（准备方法见 docs/测试指南.md「准备识别样本」）」；缺星币数标注时写 `tests\data\coins\…`，缺认角色的裁图时写 `tests\data\hero\…`，缺卡面原图时写 `tests\data\cards\…`。缺 `private.json` 时跳过的是「按记住的名字找自己那一行」那两条。第八节每节的「需要什么」里写了这个文件要不要样本、要哪些。

**这些是照开发时那一批截图写的回归测试**：识别测试不是「随便换一批截图就能跑」的通用测试，而是照开发时那一批样本写死的回归对照。一类按具体文件名、局号或拍摄时刻取样本（`test_pipeline`、`test_pipeline_sequences`、`test_resume_frames`、`test_vision_frame`、`test_prefilter`、`test_chip_select_fast`、`test_cv_threads`、`test_rapidocr_lite`、`test_stars`、`test_real_games` 里靠样本的几条、`test_selfcheck_vision` 的覆盖表），文件名或那张画面变了就按缺样本跳过，只在原样本上有意义（`test_pipeline_sequences`、`test_resume_frames` 还要求同一局、文件名以 `20261002_21` 开头的截图够 20 张）。另一类按 `labels.json`/`stars_labels.json`/`panel_labels.json` 逐条核对（`test_vision_matrix`、`test_screens`、`test_coins`、`test_chip_panel`、`test_real_games` 的样本类、`test_overlay_scenarios`、`test_project_consistency` 的样本核对），用的是你自己写的标注，可以用自己的样本；但这些文件里还有几条核对「标注覆盖得全不全」的自查（反例画面一种不缺、每种画面都有样本、标注里的名字都在资料库里），标注覆盖不全时会**失败**，不是跳过。

## 六、推荐对比工具

改了推荐规则或打分代码以后，想知道「首推变了几个」「哪些局面改了」，用基准对比工具 `tools/baseline`。它在大改前录一份基准，改完再录一份，两份逐项比对：同一批固定局面下，把推荐引擎的全部输出和显示出来的文字都录下来（首推、各选项先后、推荐度文字、位次、诊断包推荐全文、以及按方案推荐时的整套排名），两边逐项比，并算一张影响摘要——每个来源里首推变了几个、推荐度或位次变了几个、前三名先后变了几个、只有分值变了几个。命令（在仓库根目录）：

```powershell
python -m tools.baseline record 改之前        # 录一份基准（放在 .tmp/baseline/改之前/）
python -m tools.baseline compare 改之前 改之后  # 比对两份，报告写在 .tmp/baseline/compare-改之前-改之后.md
```

`compare` 不通过时（有预期以外的差异）退出码 1；两份基准的环境不一致（例如日期、哈希种子）不能比时退出码 2。要接上 `record`/`compare` 只看推荐这一个领域，用 `--only engine`；`--jobs N` 改并行路数。比对的细节和「预期变化清单」（`--expect`，把有意变化的那些登记进去、不算差异）见 `tools/baseline/` 里各模块开头的说明。

没有 git（PATH 里没有、环境变量 `GIT` 也没设）时照样录：提交号和改动状态记成缺省（不记），比对时这两项按缺省处理，见 `tools/baseline/env.py`。

这些领域各自管一块：`engine`（推荐）、`storage`（设置与方案文件的读写）、`docs`（生成文档：`review/` 下两份审查清单）、`session`（对局记录磁带）、`ui`（外观）、`vision`（识别）。`engine` 用的固定局面随仓库发布（`tests/data/baseline/engine/` 下的 gzip JSON），`docs` 和 `storage` 也不需要外部输入；其余几个领域在 `INPUTS_NEEDED` 里声明需要的外部输入（截图、本机记录等），不随仓库，缺了会给一句中文说明并退出（输入目录可用 `ACC_BASELINE_INPUTS` 指到别处）。对局记录（`session`）那一类磁带缺了会先录：环境变量 `BASELINE_QUICK=1` 只录、只放 `switch` 这一组（不用识别样本），要录的组里有用样本的、样本又不在时才给一句中文说明并退出，见 `tools/baseline/session.py`。

## 八、各测试文件

下面每个 `tests/test_*.py` 一节，按区域分章。每节的结构一样：

- **测试观点**：这个文件从哪些角度检查被测代码。
- **检证对象**：它实际测的程序文件、类或函数。
- **什么时候要跑**：改了哪些地方该跑它。
- **怎么单独跑**：`--only` 命令和这个模块上一次大约跑几秒。
- **需要什么**：要不要识别样本、显卡、真实窗口、外部程序等。
- **输出怎么看**：跑出来的结果怎么读，有没有特别的跳过或打印。
- **出错时一般是哪里不对**：失败时最可能出问题的位置，以及「有意改动时该跟着改的预期」。

各章放在 `docs/test-guide/` 下，一章一个文件：

- [推荐和打分](test-guide/engine.md)：这一章管推荐引擎：打分、理由、刷新、方案计算，以及命令行参数到对局状态的换算。改了 advisor/engine/ 或 advisor/pool.py 先看这里。
- [游戏数据](test-guide/data.md)：这一章管 data/ 下的资料库：筹码、角色、地图、规则、适配表、同系列表、畸变组件、识别图片清单，载入得对不对、字段自不自洽。改了 data/ 先跑这里的 test_check_data，再看其余。
- [识别](test-guide/vision.md)：这一章管从截图里读游戏画面的那套识别（advisor/vision）和识别流程本身：轮次、地图、候选筹码、星数、星币、面板、对局外画面，以及什么时候重读。
- [对局记录](test-guide/session.md)：这一章管一局的记账（advisor/session）、离开再回来判新一局，以及识别记录、推荐日志和对局报告的读写。
- [我的统计](test-guide/stats.md)：这一章管「我的统计」窗口和窗口里的数字（advisor/play_stats.py、advisor/ui/stats_window.py）：局数、三选一次数、跟着首推选的比例、常用角色和筹码。
- [筹码方案](test-guide/schemes.md)：这一章管筹码方案的数据结构和方案文件（`advisor/schemes.py`）、编辑窗口、导入/导出窗口和它们的列表控件。
- [悬浮窗](test-guide/overlay.md)：这一章管悬浮窗本体和拆出去的部件（advisor/ui/overlay.py、overlay_parts/）：卡片、提示、跟随与窗口层次、后台识别线程、退出收尾、全局热键，以及作业站的入口。
- [皮肤和界面控件](test-guide/skins.md)：这一章管皮肤机制和每一套皮肤、自绘部件与装饰、界面控件与文字交互，以及界面文字的守卫。
- [设置和启动退出](test-guide/settings.md)：这一章管设置文件的读写与存放位置、设置窗口、启动检查与防多开、退出收尾和错误记录。
- [系统](test-guide/system.md)：这一章管和 Windows 打交道的那一层：写盘工具、下载、屏幕与窗口截取、本机配置、诊断包。
- [软件内更新](test-guide/update.md)：这一章管软件内更新：查有没有新版本、下载并备好（有文件清单时只下变了的文件，走不通改下整包）、换版本程序、悬浮窗和设置窗口里更新的那几处，以及发版时往下载镜像传发行包的上传脚本。改了 advisor/update.py、advisor/update_files.py、advisor/update_apply.py、advisor/ui/overlay_parts/updates.py 或 tools/upload_r2.py 先看这里。
- [打包和发行版](test-guide/packaging.md)：这一章管打包发行版（tools/build_release.py）、自编 OpenCV/numpy、使用说明网页、模块分层，以及「程序用到了发行版排掉的模块」这道检查。
- [一致性和其他](test-guide/consistency.md)：这一章管跨文件的核对（版本号、首页和两份说明里的路径、样本标注、使用说明里引用的界面文字、界面文字的语体）、测试和工具的私有名字守卫、推荐对比工具几个领域的台账比对（`test_baseline_storage`、`test_baseline_docs`）、开发工具（`test_dev_tools`：校准、对着游戏窗口调试、自编 OpenCV 的逐位比对、缺识别样本时的说明），以及几处跨模块接通的测试。
